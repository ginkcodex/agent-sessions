# RF-01 — Protect the release environment and release tags

- **Status:** ✅ Done
- **Estimate:** 1 h
- **Depends on:** None
- **Plan:** [review-fixes.md](../../plan/review-fixes.md)

## Scope

The `release` environment holds `MINISIGN_KEY`, `MINISIGN_PASSWORD` and
`RPM_SIGNING_KEY`. It had no protection rules and no branch policy, so any
`workflow_dispatch` run got the keys, using the workflow file and
`cmd/release-sign` from whatever ref was chosen. Runs 43390875784 and
43504098896 on `develop` signed this way on 2026-11-13.
`docs/plan/auto-update.md` already described the environment as protected.

- Limit the environment to the `main` branch and `v*` tags.
- Add a tag ruleset for `v*`.
- Update the release workflow's comments, which said manual runs work on any
  ref.

The decisions (dry-runs only on `main`, no required reviewer, what the tag
ruleset can and can't do) are in the plan.

## Likely files

GitHub settings (no file), `.github/workflows/release.yml` (comments only),
`docs/tasks/linux-repos/LR-19.md` (manual run on `main`).

## Acceptance criteria and tests

- `gh api repos/ginkcodex/agent-sessions/environments/release` shows a
  custom branch policy.
- `…/deployment-branch-policies` lists exactly `main` (branch) and `v*`
  (tag).
- A `v*` tag ruleset is active.
- The next release publishes; a `develop` dispatch is refused at the
  artifacts job.

## Evidence

Applied on 2026-11-14 with `gh api`, as the repository admin:

- `PUT environments/release` with
  `{"deployment_branch_policy":{"protected_branches":false,"custom_branch_policies":true}}`.
  The response shows `protection_rules: [branch_policy]`.
- `POST environments/release/deployment-branch-policies`: `main` (type
  `branch`, id 66671477) and `v*` (type `tag`, id 66671479). Listing the
  policies afterwards returned exactly those two.
- Ruleset "Protect release tags" (id 27253826): target `tag`, include
  `refs/tags/v*`, rules `update` and `deletion`, bypass for the admin role
  only, enforcement `active`.
- The first attempt also had a `creation` rule with the GitHub Actions app as
  a bypass actor. GitHub refused it with `422`: "Actor GitHub Actions
  integration must be part of the ruleset source or owner organization".
  Without that bypass, a creation rule would block the release job's
  `gh release create --target`, so it was left out.
- `.github/workflows/release.yml`: only comments changed. `actionlint` is
  not installed, so the YAML was not linted.

Not checked yet:

- A real run under the new policy. The next release on `main` should
  publish.
- A `develop` dispatch should fail at the artifacts job. It wasn't run,
  because it builds everything first.
