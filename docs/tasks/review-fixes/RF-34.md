## Scope

## Evidence

CI evidence: `/tmp/as-ci-43694948130.log:22-23` records
`TestManagedJobDisconnectJoinsAndDropsConsent` failing at
`managed_tools_job_test.go:71` with `State:failed` and the generic failure message.

This is a production ordering race, not a bad test assertion or a Go data race.
`ManagedTool` creates `jobCtx` as a child of the owner context, while
`installManagedOwned` also registers `context.AfterFunc(o.ctx, cancel)` for the
installer request. When the owner is canceled, that callback can cancel the
request and let installation return before cancellation has propagated to
`jobCtx`. Terminal-state publication then sees no job cancellation and records
`failed`. The owner context is already canceled in this ordering.

Reviewed both `installManagedOwned` callers (async job and synchronous backend
seam), app/RPC forwarding, installer error sanitization, and disconnect/revoke/
engine-close removal and join paths. The fix only checks owner cancellation
alongside job cancellation when classifying an installation error. It does not
change installation, admission, consent, joins, success, or failure sanitization.

Regression: add 1,000 unused child contexts to the existing disconnect test to
widen the cancellation fan-out window. Before the fix, the modified test failed
repeatedly with the same `failed` payload in a 100-run race test. The unmodified
test had passed 1,000 local race runs. This is a scheduling stress reproduction,
not a forced-interleaving test; no production hooks or sleeps were added.
