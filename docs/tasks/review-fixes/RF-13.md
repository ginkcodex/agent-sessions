# RF-13 — The watcher recovers from transient errors

- **Status:** ✅ Done
- **Estimate:** 3 h
- **Depends on:** RF-12
- **Plan:** [review-fixes.md](../../plan/review-fixes.md)

## Scope

`watch.go:289-296, 472-490`: any fsnotify error calls `failAll`, which moves
every provider to 10 s polling for the rest of the process. `isWatchLimit`
(`:708`) is dead code. Reviewer finding.

- On `ErrEventOverflow`, rescan and keep the watches.
- Keep the fallback per provider, and try to re-install watches with backoff.
- Use or remove `isWatchLimit`.

## Acceptance criteria and tests

- Tests with a fake fs watcher: an overflow keeps watching, and an error
  falls back and later recovers.

## Evidence

Done on 2026-11-14 at `fa4f281`, in `internal/watch/watch.go`.

- An error whose cause is `fsnotify.ErrEventOverflow` queues a full rescan
  of every provider that is watching. Its watches stay.
- Any other error from the watcher's error channel still moves every
  provider to polling. Such an error names no path, so it can't be traced
  to one provider. A failure to install a watch stays per provider, as
  before.
- A provider in fallback now tries its watches again:
  - The first try waits the fallback poll interval, 10 s.
  - Each failure in a row doubles the wait, up to 32 times the interval
    (about 5 min).
  - A watch limit (`ENOSPC`, `EMFILE`) waits the longest at once. This is
    where `isWatchLimit` is now used.
  - A provider that kept its watches for that longest wait starts again
    from 10 s.
  - Once the watches are back, the provider queues a full rescan for what
    changed in between, and returns to its normal poll interval.
- No retry when the watcher itself is gone: it could not be created, or its
  channels closed. Polling continues then.
- New `recover_test.go`, with a fake filesystem watcher:
  - `TestOverflowRescansAndKeepsWatching`
  - `TestErrorFallsBackThenWatchesAgain`: a failed retry doubles the delay
    and polling goes on; the provider watches again once watches are
    allowed.
  - `TestWatchLimitWaitsLongest`
  - `TestClosedWatcherPollsWithoutRetry`
- Run against the old `watch.go`, the overflow test timed out with no
  rescan. The old code had no retry at all, so the retry tests could not
  build against it (they read the new retry fields).
- `go test -race -count=5` on the new tests passed.
- `go test -race ./internal/watch/ ./internal/engine/` passed.
- `go vet ./internal/watch/` is clean for Linux, Windows and darwin, and
  `gofmt -l` is clean.

Not checked: a real inotify queue overflow, or a real watch limit. Both are
hard to cause reliably in a test, so the fake watcher delivers the errors.
