# RF-18 — `turn_end` and open questions: one event order

- **Status:** ✅ Done
- **Estimate:** 3 h
- **Depends on:** None
- **Plan:** [review-fixes.md](../../plan/review-fixes.md)

## Scope

`internal/engine/chat.go:979-991` emits `turn_end` only after every question
has resolved. If an adapter returns `session/prompt` and never withdraws an
async question, the chat shows "working" forever. The store comment
(`chats.svelte.ts:528-531`) and the test "a question still open at turn_end
stays until its resolution" (`test/chats-store.test.mjs:681`) assume
`turn_end` can come first. Reviewer finding; see also
[CQ-08](../chat-questions/CQ-08.md).

- Pick one order. The likely choice: when the prompt returns, open questions
  turn late and `turn_end` is emitted.
- Add a Go test for a question that outlives the prompt reply, and make the
  store test match what the engine emits.

## Acceptance criteria and tests

- The Go and frontend tests describe the same event sequence.

## Evidence

- Verified the reviewer finding with a regression before fixing it:
  `TestChatQuestionOutlivesPrompt` failed after 20 seconds with a question
  and a successful steering reply but no `turn_end`. The new `acptest`
  `askhold` script leaves a form request open after its prompt returns,
  without sending adapter withdrawal.
- Chosen order: when the prompt returns, pending questions resolve as
  `question_resolved` / `withdrawn`, then `turn_end` is emitted after those
  handlers and existing permission/steering waits drain. The adapter gets
  a cancelled form response; the store retains its existing late card so
  the user can send the answer as a new message. Questions racing admission
  after prompt completion are cancelled rather than holding the turn open.
- The regression checks resolution before turn end, no pending question or
  working state afterwards, stale answer refusal, a subsequent successful
  turn, and contiguous event sequence numbers. The frontend store test now

  and verifies late cards survive later turns until chat exit.
