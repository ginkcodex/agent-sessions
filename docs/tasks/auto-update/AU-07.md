# AU-07 — macOS: apply on restart or quit

- **Status:** ✅ Done
- **Estimate:** 3.5 h
- **Depends on:** AU-04, AU-06
- **Plan:** [auto-update.md](../../plan/auto-update.md)

## Scope

- `--apply-update <ready folder>`: the app copies its executable to a
  temporary folder and starts the copy in this mode, then quits.
- The copy waits for the app's process to exit, renames the installed
  bundle aside, renames the staged one into place, starts it with `open`,
  and deletes the old bundle. On any failure it puts the old bundle back
  and starts it.
- It logs to the updates folder; the next launch reports a failure through
  the update state.

## Likely files

`cmd/agent-sessions/main.go`, `internal/update/apply_darwin.go`, tests.

## Acceptance criteria and tests

- Tests on temporary bundles: success, failure after the first rename
  (rolled back), and a process that never exits (gives up, leaves the app
  installed).

## Evidence

Done:

- `internal/update/apply.go`: `Swap` waits for the app to quit, takes the
  updates lock, re-runs `Mac.Eligible` and the full `verify` (including
  Gatekeeper) on the staged copy, renames the bundle to
  `.<App>.old-<version>`, renames the staged copy into place, opens it with
  `open` in a restart, and deletes the old bundle. A failed second rename or
  a failed `open` moves the new app back to its staged name, puts the old
  bundle back and, in a restart, opens it. A swap cut off earlier (old app
  aside, nothing in place) is repaired first.
- `internal/update/apply_darwin.go`: `StartApply` copies the executable to a
  temporary folder and starts the copy detached (`Setsid`) with
  `--apply-update <ready folder> --bundle <app> --pid <n> [--relaunch]`;
  `ApplyMain` runs it, logs to `apply.log` in the updates folder and removes
  its own copy on exit. `waitExit` polls `kill(pid, 0)` for up to 2 minutes.
- A failed install calls `Store.GiveUp`, which sets the version's failure
  count to the maximum. `Manager.Offer` and `Manager.Resume` check that
  before the ready shortcut, so the next launch shows the release page
  (`manual`) instead of installing again. A newer release starts over. An
  app that never quit is not a failure.
- `cmd/agent-sessions/main.go` calls `update.ApplyMain` first. On other
  platforms it never answers.
- `internal/app/update_darwin.go` turns macOS updating on: `canSelfUpdate`
  (release build, inside a bundle, `Eligible`; computed once), `prepareUpdate`
  (`Stage`, then `Cleanup` of other versions) and `applyUpdate`
  (`StartApply`). Other builds stay `unsupported`.

Verified:

- `go test -race ./internal/update ./internal/app ./cmd/agent-sessions`:
  pass. New tests on temporary bundles with the fake system tools: success,
  restart opens the new app, failure after the first rename (old app back and
  opened), new app that will not open (rolled back), cannot move the old app
  aside, process that never quits (app untouched, staged copy kept), staged
  copy re-checked (bad signature, other team, Gatekeeper), repair of a cut
  off swap, and a failed install sending the user to the release page. On
  darwin: `waitExit` against a real process and the helper's argument check.
- `go vet` for darwin, linux, windows and `-tags desktop,production`.
- Ran the built binary as `--apply-update` against an unsigned bundle: it
  waited for the given pid, refused, wrote `apply.log`, recorded the failure
  and left the bundle alone.

Not checked: a swap with the real signed app and the real `open` (AU-08, on
a Mac with a published release); the helper surviving the app's exit when
the app is launched from Finder.
