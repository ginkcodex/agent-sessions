# AU-03 — Download, check and keep the ready version

- **Status:** ✅ Done
- **Estimate:** 3 h
- **Depends on:** AU-02
- **Plan:** [auto-update.md](../../plan/auto-update.md)

## Scope

- Download the installer to `<user cache>/agent-sessions/updates/<version>/`
  while holding a lock (`internal/filelock`), so one process downloads.
- Check size and SHA256 before marking the folder ready (a `ready.json`
  with version, file and hash). Remove older version folders and partial
  downloads.
- Count failures per version; after three, report "manual" so the frontend
  shows today's toast.
- A ready version that is no longer the latest (pulled on GitHub) is
  removed at the next check.

## Likely files

`internal/update/download.go`, `internal/update/download_test.go`.

## Acceptance criteria and tests

- Two processes started together: one downloads, the other sees it ready.
- A truncated or altered download is deleted and never marked ready.
- A pulled version's ready folder is removed.

## Evidence

Built as `update.Store` (`internal/update/download.go`): `Fetch(ctx, Release)`
downloads to `<dir>/<version>/<file>.part`, hashes while writing, compares
size and SHA256 with the verified `Release`, renames, and only then writes
`ready.json`. `Ready`, `Newest`, `Failures`, `GaveUp` and `Reconcile(keep)`
(removes other version folders, partials, a pulled version, and failure counts
for other versions; leaves the lock and other files such as the apply log).
`Ready.Verify` re-hashes for the installer to call before use. The download has
no overall timeout, only a 60 s idle timeout, since installers are large.
Cancelling is not counted as a failure.

Ran: `go test -race ./internal/update` (passes; the timing tests also passed
3 times in a row), `GOOS=windows go vet ./internal/update`. Tests cover:
download and ready marker; no second download when ready; an altered,
truncated or 404 download leaves nothing behind and is never ready; a stale
marker or `.part` is replaced; three failures give up and persist across
`Store`s, success clears the count, another version starts fresh; cancel is
not a failure; a stalled download is abandoned while a slow steady one is not;
two stores on one folder download once; waiting for the lock honours the
context and `Reconcile` reports busy without removing anything; unusable
releases and forged markers are refused; `Reconcile` keeps only the latest,
removes a pulled version and leaves the log.

Not checked: two real processes (the test uses two `Store`s with separate file
descriptors, which `flock` and `LockFileEx` treat as separate holders;
`internal/filelock` has its own cross-process tests); Windows runtime (only
cross-vetted); nothing calls `Store` yet, that is AU-04.
