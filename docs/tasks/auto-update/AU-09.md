# AU-09 — Windows: check and prepare the MSIs

- **Status:** ✅ Done
- **Estimate:** 3 h
- **Depends on:** AU-03
- **Plan:** [auto-update.md](../../plan/auto-update.md)

## Scope

- Possible only when the running exe is in the product's install folder
  and Windows Installer lists exactly one per-user product with the
  UpgradeCode, at the running version. Test builds
  (`agent-sessions-launchN`) and portable copies are `unsupported`.
- Download the new MSI and the installed version's MSI (for rollback);
  check both against their releases' signed `SHA256SUMS`.
- Check each MSI's UpgradeCode and ProductName, moving the code
  `packaging/windows/setup` uses into a package both can import.

## Likely files

`internal/update/windows.go`, `internal/winmsi/` (moved from
`packaging/windows/setup/msi_windows.go`), tests.

## Acceptance criteria and tests

- Tests with fake registry readers for each eligibility case.
- Setup's existing tests pass after the move.
- `GOOS=windows go vet ./...` passes; native run in AU-11.

## Evidence

Done:

- `internal/winmsi` (new): the MSI reading moved out of
  `packaging/windows/setup`: `ParseVersion`, `Version.NewerThan`,
  `ValidGUID`, `ForRelease`, `Info.Check` (UpgradeCode, ProductName, per-user,
  version) work on every platform; `ReadInfo`, `Validate`,
  `InstalledProducts` and `ProductCode` (`winmsi_windows.go`) use msi.dll as
  before. Setup keeps its names as thin wrappers (`msi_windows.go`, `flow.go`)
  and `build-setup.sh` copies `internal/winmsi` into the staged build.
- `internal/update/windows.go`: `Windows.Eligible` needs the running exe to be
  `%LOCALAPPDATA%\Programs\Agent Sessions\agent-sessions.exe` and one
  unmanaged product for the current user whose version is the running one.
  `Windows.Prepare` checks the new MSI and downloads and checks the installed
  version's MSI, refusing an older version. `windows_windows.go` has the real
  registry, SID and MSI readers.
- `Checker.FeedFor(version)` reads any release's `SHA256SUMS` through its
  signature, for the rollback MSI. `Store.FetchRollback` keeps it in
  `<new version>/rollback/`, so removing a version removes its rollback, and
  its failure does not count against the new version. `ReadReady(dir)` is the
  marker reader `Store.Ready` now uses.

Decision: the install folder is the fixed `INSTALLDIR` of the MSI
(`%LOCALAPPDATA%\Programs\Agent Sessions`; the installer offers no choice
and the MSI does not set `ARPINSTALLLOCATION`), so the registry check is that
exactly one current-user product of the running version exists, not a path
read from the registry.

Verified:

- `go test -race ./internal/update ./internal/winmsi ./packaging/windows/setup`:
  pass. Windows tests use fake product and MSI readers: eligibility (test
  build folder, portable copy, other exe, none/two/machine-wide/managed/other
  user's product, other version, bad code, unreadable registry), packages that
  are not ours (UpgradeCode, name, version, machine-wide, unreadable, for both
  MSIs), an older version, a rollback download that fails its signed hash, an
  offline second run, cleanup with the version. `FeedFor`: signed release,
  wrong key, unsigned, sums of another version, bad names.
- `GOOS=windows go vet` for `internal/update`, `internal/winmsi`,
  `packaging/windows/setup`, `internal/app`, `cmd/agent-sessions`; the
  staged `-tags setupbundle` build of setup, copied the way `build-setup.sh`
  does, compiles for windows/amd64.

Not checked: anything against the real Windows Installer or registry (the
setup package's native tests and `winmsi_windows_test.go` run in Windows CI
and in AU-11); `build-setup.sh` end to end (no `windres` here).
