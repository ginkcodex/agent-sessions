# AU-16 — macOS: the update helper is killed on start

- **Status:** ✅ Done
- **Estimate:** 2 h
- **Depends on:** AU-07
- **Plan:** [auto-update.md](../../plan/auto-update.md)

## Problem

Found in a hand test on 2026-11-13: a Developer ID signed 1.5.5 (built from
develop) downloaded and staged 1.5.6 from GitHub. **Restart now** quit the
app, and nothing was installed or reopened. On the next launch the app showed
**Update ready** again, and every Restart now did the same.

`StartApply` copied only the executable to `$TMPDIR` and started it. A
Developer ID executable with the hardened runtime is bound to its bundle's
`Info.plist`, and macOS kills a bare copy with SIGKILL as it starts. The
helper never wrote `apply.log`, and its copies were left in `$TMPDIR`.
`cmd.Start` had succeeded, so the app thought an installer had taken over,
quit and did not restart itself. The unit tests ran unsigned binaries, which
macOS does not kill this way.

The same helper shipped in 1.5.6, the first release with auto-update, so
1.5.6 installs cannot update themselves.

## Scope

- Copy the whole running bundle for the helper (a `clonefile` APFS clone
  where possible, or a plain copy) to `<updates>/helper/agent-sessions-apply-*/`.
  That folder is removed by its exact path at the next `StartApply`, as on
  Windows.
- Have the helper report in on a pipe (fd 3, `--notify-fd 3`) once it runs.
  The app waits up to 20 s and kills a helper that exits, closes the pipe or
  stays silent. `StartApply` then fails, so `Finish` reports that no
  installer took over and a restart opens the old app again.
- `Manager.Finish` marks a version whose installer could not start as given
  up, as the helper does for a failed install. The next launch shows the
  release page instead of failing at every quit.
- Plan: the Installing section and the Risks note for 1.5.6 users.

## Likely files

`internal/update/apply_darwin.go`, `internal/update/apply.go`,
`internal/update/manager.go`, tests.

## Acceptance criteria and tests

- A helper that is killed, exits early, closes the pipe or stays silent
  makes `StartApply` fail, and the helper is reaped.
- The bundle copy keeps files, permissions and symbolic links, by clone and
  by copy.
- An opt-in test runs the copied helper of a real Developer ID app
  (`AGENT_SESSIONS_SIGNED_APP`) and gets its usage exit, not a kill.
- The 1.5.5 → 1.5.6 hand test above updates and reopens 1.5.6 (part of
  AU-08).

## Evidence

- Cause shown by hand on the signed 1.5.5 in `/Applications`, running the
  helper with missing arguments (usage exit 2 means it ran):
  - inside the installed bundle: exit 2;
  - a bare copy in `$TMPDIR`, as `StartApply` made it: exit 137 (SIGKILL), and
    `codesign --verify` says "invalid Info.plist";
  - a copy inside a bundle with `Info.plist` and `_CodeSignature`: exit 2;
  - a `ditto` copy of the whole bundle: exit 2.
- New tests in `apply_darwin_test.go`: `TestStartHelperWaitsForTheHelperToReportIn`,
  `TestStartHelperReportsAHelperThatCannotRun` (killed, exit 2, pipe closed),
  `TestStartHelperGivesUpOnASilentHelper`, `TestCopyBundleKeepsFilesModesAndLinks`
  (clone and copy), and `TestSignedHelperCopyRuns`.
  - `TestFinishFailingToApplyLeavesTheAppToRestartItself` now also checks
    that the version is given up.
- `go test ./internal/update/ ./internal/app/`: pass on macOS (Darwin arm64).
- `AGENT_SESSIONS_SIGNED_APP="/Applications/Agent Sessions.app" go test
  ./internal/update/ -run TestSignedHelperCopyRuns`: pass against the
  Developer ID (8C8LBMDS27) 1.5.5 build.
- `go vet ./internal/update/` for darwin, windows and linux: clean.
- Not yet checked: a full 1.5.5 → 1.5.6 update with a signed build that
  has this fix (to do in AU-08). The Windows helper is unchanged; it still
  copies only the `.exe`, which Authenticode does not tie to a folder, and
  is still to be tried on Windows in AU-11.
