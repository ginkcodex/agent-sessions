# AU-17 — Windows helper reports in; a restart always brings the app back

- **Status:** 🟡 Partial — the Windows tests are built but have not run on
  Windows yet (CI's `windows-latest` job runs them on the next push)
- **Estimate:** 2.5 h
- **Depends on:** AU-10, AU-16
- **Plan:** [auto-update.md](../../plan/auto-update.md)

## Problem

A review of the Windows update after AU-16 found the same class of fault:

- `StartApply` counted a started process as an installer that took over. A
  helper that dies at once (antivirus, a policy, a crash) would quit the app
  for nothing, as on macOS before AU-16. Copying the `.exe` alone is fine on
  Windows: Authenticode does not tie it to a folder, and its manifest
  (`asInvoker`, system Common Controls only) needs nothing beside it.
- On both systems, a helper that stopped after the app quit but before it
  touched the installed app did not start it again in a restart:
  - macOS `Swap`: the lock, the eligibility check, the staged app's checks,
    clearing an old backup, moving the app aside.
  - Windows `MSIApply`: the lock, the new and rollback MSIs' checks, reading
    the installed product.
  - Windows `runApply`, before `MSIApply`: reading the user, the ready
    folder, the rollback MSI, finding `msiexec`.

  **Restart now** then ended with no app open.

## Scope

- Shared `awaitHelper` and `reportStarted` (`apply.go`). The macOS helper
  (fd 3) and the Windows helper (an inheritable pipe handle passed as
  `--notify-handle`, and only that one through `AdditionalInheritedHandles`)
  both report in. The app waits up to 20 s, and kills and reaps a helper that
  exits, closes the pipe or stays silent.
- Windows `startDetached`: the breakaway-then-plain start, with the
  handshake. A helper that started and then failed is not started a second
  time.
- `Swap.reopen` and `MSIApply.stopped` start the untouched installed app in
  a restart. The Windows helper's early failures wait for the app to exit,
  then start the installed one.

## Likely files

`internal/update/apply.go`, `apply_darwin.go`, `apply_windows.go`,
`apply_msi.go`, tests.

## Acceptance criteria and tests

- macOS and Windows: a helper that is killed, exits, or stays silent makes
  `StartApply` fail.
- Windows: a real detached child gets the pipe handle and reports in.
- Every failure before the installed app is touched starts it again in a
  restart, and not after a plain quit.
- On Windows: a hand test where the helper is blocked, and one with an MSI
  changed after download, both end with the old app open (AU-11).

## Evidence

- New `apply_windows_test.go`. The test binary is started as the helper
  (`TestHelperProcess`) through `startDetached` with the real creation
  flags, and covers: it reports in, it exits 3, it stays silent (2 s
  timeout), and the program is missing.
- `apply_test.go`: the staged-app checks (bad signature, another team,
  Gatekeeper) and the failed move aside now also expect the old app to be
  opened in a restart. They expect nothing opened after a plain quit. New:
  `TestSwapThatCannotLockReopensTheAppInARestart`.
- `apply_msi_test.go`: altered new or rollback MSI, a second registration,
  and the lock held now expect the installed app started in a restart, and
  not after a plain quit.
- The macOS handshake tests from AU-16 now run through the shared
  `awaitHelper`.
- `go test ./internal/update/ ./internal/app/`: pass on macOS (Darwin arm64).
  `TestSignedHelperCopyRuns` against the Developer ID app in `/Applications`:
  pass.
- `go vet` of `internal/update` and `internal/app` for darwin and windows,
  and of `internal/update` for linux: clean.
- `GOOS=windows go test -c ./internal/update/`: builds.
- Not run: the Windows tests on Windows. They run in CI's `windows-latest`
  job, which runs `go test ./...`, and still need a real update in AU-11.
- The user's hand test of AU-16 (signed 1.5.5 → 1.5.6 with **Restart now**)
  passed on 2026-11-13, before this change.
