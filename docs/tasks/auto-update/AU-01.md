## Scope

- The maintainer generates two minisign key pairs, a primary and a backup,
  and keeps offline encrypted copies. The primary's secret key and password
  become secrets of a protected `release` environment.
- The release job signs `dist/SHA256SUMS` after `release-checksums.sh`,
  writing `SHA256SUMS.minisig` with a trusted comment naming the version,
  and checks it with the public key. It is in `dist/` before
  `gh release create`, so no published release ever lacks it; a rerun's
  `gh release upload --clobber` uploads both files together.
- Without the secrets the step skips signing with a warning and the release
  is published unsigned (installed apps then only show the old notice). To be
  tightened to a failure for publishing runs once the secrets exist.
- Both public keys go in `internal/update/keys.go` and in the README.

## Likely files

`.github/workflows/release.yml`, `cmd/release-sign/`, `internal/update/keys.go`, `README.md`.

## Acceptance criteria and tests

- `minisign -Vm SHA256SUMS -p primary.pub` passes on the release's files.
- `actionlint` passes.
