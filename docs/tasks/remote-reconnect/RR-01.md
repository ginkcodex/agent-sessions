# RR-01 — Phase-timing log, silent-failure scenarios and baseline

- **Status:** ⬜ Not started
- **Estimate:** 3 h
- **Depends on:** —
- **Plan:** [remote-reconnect.md](../../plan/remote-reconnect.md)

## Scope

- Log each connection phase change with the host, the new phase, the time
  spent in the previous phase and the error text, one line per change
  (`agent-sessions: connection <host>: reconnecting after 21.3s connected
  (connection lost)`). Never log askpass answers or environment values.
- Add two scenarios to the opt-in Docker sshd harness, run at production
  timings (no shortened backoff for the detection part):
  - **Network cut:** connect, `docker network disconnect` the container,
    wait for `reconnecting`, reconnect the network, wait for `connected`.
  - **Frozen host:** the same with `docker pause` / `docker unpause`.
  Each records the two durations and logs them with `t.Logf`. Upper
  bounds are generous on purpose here (they measure today's code); RR-07
  tightens them.
- Run both against the current code and record the baseline in
  [remote-reconnect-qa.md](../../plan/remote-reconnect-qa.md).

## Likely files

`internal/app/remote.go` (`setPhase`), `internal/app/sshd_test.go`,

## Acceptance criteria and tests

- A unit test checks the log line for a connect, a drop and a reconnect,
  using an injected clock or logger, and that nothing secret is logged.
- `make test-ssh` runs the two scenarios; they are skipped without
  `AGENT_SESSIONS_SSH_DOCKER=1`, like the other sshd tests.
- The baseline table lists both scenarios with durations, date and commit.
  If a scenario never recovers within its bound, that is recorded as the
  result, not treated as a harness failure to work around.
