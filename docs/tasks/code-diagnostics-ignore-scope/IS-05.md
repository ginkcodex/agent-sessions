# IS-05 — Files, Changes and History: Git without `core.fsmonitor`

- **Status:** ✅ Done
- **Estimate:** 2 h
- **Depends on:** —
- **Plan:** [code-diagnostics-ignore-scope.md](../../plan/code-diagnostics-ignore-scope.md)

Found while planning IS-01: `gitOutputEnv` in `internal/files` runs Git
without `-c core.fsmonitor=false`. A repository's own `.git/config` can set
`core.fsmonitor` to a program, and `git status` / `ls-files` start it, so
opening a project's file tree can run a program the project chose.

## Scope

- Decide whether every Files, Changes and History Git call passes
  `-c core.fsmonitor=false`, or only the read-only listing calls. Turning it
  off loses the built-in fsmonitor daemon's speed-up in repositories that
  use it; record the measured cost.
- Apply it, with a test that a configured fsmonitor script does not run for
  the listing, status and history calls.

## Likely files

`internal/files/files.go`, `git_history_*.go`, tests.

## Acceptance criteria

- A repository with `core.fsmonitor` set to a script: opening the file tree,
  Changes and History does not run it.

## Decision

Every Git call in `internal/files` turns `core.fsmonitor` off, writes
included: the listing, status, diff, blame and History reads, and the
Changes and History actions (`gitWriter.run`). One shared flag
(`gitNoFsmonitor`) in the four runners (`gitOutputEnv`, `GitRepoStatus`'s
runner, `blameGit`, `gitWriter.run`) is simpler to keep right than a list of
read-only calls, and staging or committing would otherwise start the program
too. `IgnoredDirectories` no longer passes the flag itself.

Cost: Git's built-in daemon (`core.fsmonitor=true`) is turned off with any
configured program. It exists on Windows and macOS only (`git
fsmonitor--daemon` on Linux: "not supported on this platform"), so the cost
could not be measured here; without it, `git status` in this checkout
(3316 files) takes under 10 ms. Very large repositories on Windows or macOS
that rely on the daemon lose its speed-up.

## Evidence

- `internal/files/files.go`: `gitNoFsmonitor`, added by `gitOutputEnv`;
  `repo_status.go`, `blame.go`, `git_write.go` add it to their argv.
  `git_history_compare.go`'s `diff --no-index` runs in a temporary folder
  outside any repository and is unchanged.
- `fsmonitor_test.go` (real `git` 2.53.0): a repository with
  `core.fsmonitor` set to a script that writes a marker. `List`,
  `ListingStatus`, `ListDirectory`, `IgnoredDirectories`, `GitRepoStatus`,
  `ReadGitDiff`, `BlameFile`, `GitHistoryRepositories`, `GitHistoryBranches`
  and `GitHistoryList` run without the script running. With the runners
  reverted the test fails for `List`, `ListingStatus`, `GitRepoStatus`,
  `ReadGitDiff`, `BlameFile` and `GitHistoryRepositories`.
- `go test -count=1 ./internal/files/ ./internal/codediagnostics/
  ./internal/app/... ./internal/engine/` passes. `go tool golangci-lint run
  ./internal/files/` (no caps): the same four findings in the changed files
  before and after (`blame.go` and `files.go` errcheck, `git_write.go` and
  `repo_status.go` gofumpt), none on changed lines.
- Not checked: Windows and macOS Git, the desktop app, Changes and History
  actions (staging, commit) with a configured script (they share
  `gitWriter.run`, which the History reads cover).
- Found along the way: `git status` also runs a clean filter
  (`filter.<name>.clean`) that the repository's config sets, for a file
  whose stat changed. Tracked as [IS-06](IS-06.md).
