## Scope

- The Manager orders a document's completion requests by `completionSeq`
  and keeps the answer with the latest one. The session orders them
  separately, by the order they reach `beginCompletion`. The two orders can
  differ. Request A takes seq 1 and B seq 2, but B reaches the session first
  and is kept as result `1`; the Manager keeps B. A then begins as result
  `2`, answers, and the session replaces B's items with A's. The Manager
  refuses A as older, so it still points at result `1`, which the session no
  longer holds. Every resolve of the suggestions shown for B fails with
  staleVersion, and an import that comes only on resolve (vtsls) is lost.
- `CompletionRequest.Order` carries the Manager's seq. `beginCompletion`
  makes a request pending only when its order is later than every order
  begun for the URI, so the session keeps an answer only when the Manager
  would. Order 0 (direct callers and tests) is after every request begun.
- The order outlives a failed request and an answer dropped for the byte
  cap: such slots stay, without items, until the document is closed or
  reopened.

## Done when

- A request ordered earlier that starts later is not kept by the session.
- The Manager passes its seq to the provider.
