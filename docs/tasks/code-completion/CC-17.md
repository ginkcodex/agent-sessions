# CC-17 — Review fixes: late answers, awaited items and language labels

- **Status:** ✅ Done
- **Estimate:** 3 h
- **Depends on:** CC-06, CC-12, CC-14
- **Plan:** [code-completion.md](../../plan/code-completion.md)

## Found by

A second code review of the `feature/code-completion` branch.

## Scope

All in `fileEditor.ts`:

- **A cancelled query writes nothing.** `codeSuggestions` records the
  learned trigger characters and the unfinished word from an answer even
  when CodeMirror aborted the query. Only the 1.5 s timeout is covered
  today. A stale unfinished entry makes the next keystroke ask as
  `incomplete` instead of `invoked`. An aborted query writes nothing, and
  the unfinished word is kept only while the document is the one asked
  about.
- **An awaited item whose word is gone goes nowhere.** After typing during
  the import wait (CC-12), the item replaces the mapped range. When the
  user deleted or replaced the whole word meanwhile, that range is empty,
  and the item would still be put in there. A pick whose range was not
  empty and is now empty is dropped.
- **Language labels without doing the work twice.** `languageLabels` runs
  each language source again to know its labels. That second run has no
  link to the query's cancellation, and for an async source it does the
  whole work for nothing. A source seen to answer with a promise is not run
  again for labels. Words it offers may then repeat its items, which
  CodeMirror shows as two rows; no language package used here answers
  asynchronously today.

## Done when

- An answer for an aborted query leaves the trigger and unfinished state as
  they were.
- Deleting the word during the wait puts nothing in; typing elsewhere still
  does (CC-12).
- An async language source is run once per query, not twice.

## Tests

- `file-editor.test.mjs` (jsdom): an aborted query's answer does not
  change the next trigger kind; a deleted or replaced word during the wait
  gets no item, and undo history is unchanged; an async language source
  runs once per query after its first answer.

## Done

- **Aborted queries.** `codeSuggestions` returns nothing for an answer to a
  query CodeMirror aborted, before writing the learned trigger characters
  or the unfinished word.
  - The unfinished word is kept only while it is still where it was asked
    (`sameWord`): the same document, or one typed on after the word.
  - Not `doc === askedDoc` alone, as the review suggested. CodeMirror keeps
    a query running through plain typing (`onDocChange` is off), so typing
    on during a request is the usual case, and its next keystroke should
    still ask as `incomplete`.
- **A pick whose word is gone.** The pending pick's state field marks it
  `gone` when one change covers all of the text it replaces: the word
  deleted at once, typed over, or deleted down to its last character.
  `settle` then clears the pick and puts nothing in.
  - The review's check, a range that became empty, misses typing over: the
    mapped range then covers the new text, and the item would replace it.
  - A shortened word is still replaced by the item, and typing at either
    end stays outside, as before.
- **Async language sources.** `languageLabels` remembers a source that
  answered with a promise (`asyncSources`) and does not run it again for
  labels. Sources that answer at once still run on every query.

## Evidence

Run on macOS arm64, 2026-11-18:

- `file-editor.test.mjs` (jsdom), new tests:
  - **An aborted query.** Its incomplete answer, with trigger characters
    `.`, leaves the next keystroke asking as `invoked`, and `:` still
    triggers. Not aborted, but typed on in the same word: the next
    keystroke asks as `incomplete`. A word changed before the answer came:
    `invoked`.
  - **An awaited item.** If its word is deleted, typed over, or deleted one
    character at a time, nothing goes in and the undo history is unchanged.
    If the word was shortened, the item goes in as one undo step.
  - **An async language source.** Over 3 queries it runs once; a sync
    source runs 3 times.
- All three tests fail on the previous `fileEditor.ts` and pass now.
- `npm test` (1600 pass, 4 skipped, 0 fail), `npm run check` (0 errors),
  `npm run build`. The headless Chrome file passes 3 runs in a row.
