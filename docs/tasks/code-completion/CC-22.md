# CC-22 — Review fixes: cancel resolves, drop resolves for old versions

- **Status:** ✅ Done
- **Estimate:** 3 h
- **Depends on:** CC-04, CC-12
- **Plan:** [code-completion.md](../../plan/code-completion.md)

## Found by

A third code review of the `feature/code-completion` branch (`/code-review develop...feature/code-completion`), checked against the code before this task was written. The store cleanup came from a separate review note on `codeDiagnostics.svelte.ts:364-365`.

## Scope

- **Resolves can be cancelled.** `ResolveCodeCompletion` runs under the
  app's context with no request ID, and the editor's `AbortSignal` never
  reaches the host. Moving through the popup asks for each selected item's
  details, up to 5 s each, and none is cancelled, which queues them over
  SSH. The binding takes a request ID, as `CompleteCode` does, and
  `CancelCodeCompletion` cancels it. The store cancels a resolve once no
  one waits for it any more: the info panel moved to another item or the
  popup closed, and no accept waits for it.
- **Old versions' resolves are dropped.** The store keeps a resolve per
  `index@version` for the answer's whole life, with its documentation and
  edits. Only the current version is read again, so entries for other
  versions are dropped when a newer version is asked; version 0 entries,
  which `details` reuses, stay.

## Done when

- A resolve nobody waits for is cancelled on the host.
- The store holds resolves for version 0 and the latest version only.

## Tests

- App: a resolve under a request ID is cancelled by `CancelCodeCompletion`.
- Frontend: the API passes the request ID; moving the selection cancels the
  previous item's resolve; an accept waiting on it keeps it; a newer version
  drops the older version's entries and keeps version 0.

## Evidence

What changed:

- `App.ResolveCodeCompletion` takes a request ID and runs under
  `a.completions`, as `CompleteCode` does, so `CancelCodeCompletion` cancels
  it and the call returns `canceled`. The engine and RPC paths already
  passed the context through, so the language server gets
  `$/cancelRequest` locally, and over SSH and WSL in turn.
- The frontend API, the backend interface and the mock take the request ID.
- The store gives each resolve its own request ID and counts who waits for
  it. Each waiter's signal is released when it aborts; a waiter without a
  signal waits until the resolve ends. Once nobody waits, the store cancels
  the resolve on the host and forgets it, and the next ask starts another.
  `details(index, signal)` passes the info panel's signal. `extraEdits`
  joins the resolve at the shown version straight away, before it sends
  pending typing, so closing the popup on accept does not cancel the info
  panel's resolve that the accept waits for. An accept that gives up after
  its wait aborts its signal, which cancels a resolve only it waited for.
- Asking at a newer version drops the answer's resolves, in flight and done,
  for every version other than 0 and the new one. A resolve dropped while in
  flight is not stored when it ends.
- The editor keeps, per view, the info panel's wait and the state it asked
  in. CodeMirror shows the details only while its completion state stays the
  same, so the wait is aborted when another item is asked for (after the new
  ask, so the same item again keeps its resolve), when the text, selection,
  selected item or completion status changes, and when the editor's state is
  replaced (the plugin is destroyed).

Tests, all run on macOS:

- Go: `go test -count=1 ./internal/codediagnostics/... ./internal/rpc/...
  ./internal/app/... ./internal/engine/...` passed. The local live route
  test now holds a resolve at the fake server, cancels it with
  `CancelCodeCompletion("r2")`, expects `canceled` within 2 s (the resolve
  timeout is 5 s), and waits for the server to get `$/cancelRequest` for
  that resolve. With the resolve back on the app context, the test fails
  ("cancel did not end the resolve"). `GOOS=windows` and `GOOS=linux`
  `go vet` on app, rpc and codediagnostics passed; `go build ./...` and the
  Windows CLI build passed.
- Frontend: `npm test` 1606 pass, 0 fail; `npm run check` 0 errors;
  `npm run build` passed.
  - `code-completion.test.mjs`: the Wails binding gets the request ID
    first.
  - `live-lifecycle-integration.test.mjs`, "a resolve nobody waits for is
    cancelled…": moving off an item cancels its resolve under its request
    ID, and asking again starts another; the same item asked twice is
    asked once and kept when the first wait ends; an accept waiting on the
    info panel's resolve keeps it when the panel's wait ends; an accept
    that gives up cancels a resolve only it waited for. Without the cancel,
    or without the early join in `extraEdits`, the test fails.
  - "an answer keeps resolves for version 0 and the latest version only":
    the store's maps are private, so the test uses `--expose-gc` and
    `WeakRef`s on the resolved objects. After a newer version is asked, the
    old version's resolves, including one still answering, are collected;
    version 0's stays and is read again without a new ask. Without the
    eviction, or with a dropped resolve still stored when it ends, the test
    fails.
- Chrome (`file-editor-chrome.test.mjs`, 4 pass), new test "the details
  panel stops waiting…": with details that never come, ArrowDown aborts the
  first item's wait and Escape aborts the second's. Without the plugin, or
  without the abort when another item is asked for, the test fails.

Not checked:

- Cancelling over a real SSH or WSL host. The RPC client and server already
  carry cancels for `completeCode` the same way.
- A real language server's handling of `$/cancelRequest` for
  `completionItem/resolve`.
- The editor tracks CodeMirror's private completion state through public
  signals. A change it cannot see (new options with the same item selected,
  same status and no edit) leaves the wait running until the resolve ends,
  as before this task. When the options change, CodeMirror asks for the
  item's details again, which ends the earlier wait.
