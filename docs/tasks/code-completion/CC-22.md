## Scope

- **Resolves can be cancelled.** `ResolveCodeCompletion` runs under the
  app's context with no request ID, and the editor's `AbortSignal` never
  reaches the host. Moving through the popup asks for each selected item's
  details, up to 5 s each, and none is cancelled, which queues them over
  SSH. The binding takes a request ID, as `CompleteCode` does, and
  `CancelCodeCompletion` cancels it. The store cancels a resolve once no
  one waits for it any more: the info panel moved to another item or the
  popup closed, and no accept waits for it.
- **Old versions' resolves are dropped.** The store keeps a resolve per
  `index@version` for the answer's whole life, with its documentation and
  edits. Only the current version is read again, so entries for other
  versions are dropped when a newer version is asked; version 0 entries,
  which `details` reuses, stay.

## Done when

- A resolve nobody waits for is cancelled on the host.
- The store holds resolves for version 0 and the latest version only.

## Tests

- App: a resolve under a request ID is cancelled by `CancelCodeCompletion`.
- Frontend: the API passes the request ID; moving the selection cancels the
  previous item's resolve; an accept waiting on it keeps it; a newer version
  drops the older version's entries and keeps version 0.
