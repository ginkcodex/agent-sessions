# CC-04 — Completion over the wire

- **Status:** ✅ Done
- **Estimate:** 3 h
- **Depends on:** CC-02, CC-03
- **Plan:** [code-completion.md](../../plan/code-completion.md)

## Goal

Make completion, resolve and cancel available to the frontend for local
projects and over SSH and WSL, as NAV-02 did for navigation.

## Scope

- `engine.CodeCompletionBackend`, its own interface so the diagnostics and
  navigation contracts do not change. The local engine and `rpc.Client`
  implement it.
- App bindings, routed through `liveRoute` with the host and epoch checks:
  - `CompleteCode(context, requestId, documentId, version, position, trigger, expectedHostId)`
  - `ResolveCodeCompletion(context, documentId, resultId, index, expectedHostId)`
  - `CancelCodeCompletion(context, requestId, expectedHostId)`: cancels the
    request's context; an unknown ID is a no-op.
- RPC: `completeCode`, `resolveCodeCompletion` and `cancelCodeCompletion` in
  the live method list with the ownership check. A `codeCompletion`
  capability is set only with `liveCodeDiagnostics`. The client refuses an
  older server before any work, and checks the answer matches the request.
- Frontend: types, `api.completeCode`, `api.resolveCodeCompletion` and
  `api.cancelCodeCompletion`; the mock backend in
  `frontend/src/lib/mock/codeDiagnostics.ts`; regenerated bindings.

## Done when

- A local and a fake remote request return the same normalized answer.
- Cancel stops an in-flight request on both paths.
- An older remote host reports no `codeCompletion`, and calls fail with
  `unsupported` without reaching it.

## Tests

- App, engine and RPC tests: routing, stale host or epoch, the capability
  flag, cancel, mismatched answers.
- Frontend API test for the bindings and the missing-binding case.
- `go test ./...`, `npm run check`, `npm test`.

## Done

- Engine: `engine.CodeCompletionBackend` (`CompleteCode`,
  `ResolveCodeCompletion`), implemented by the Engine, `rpc.Client` and
  `UnsupportedCodeDiagnostics`.
- App (`internal/app/code_completion.go`): `CompleteCode(context, requestId,
  documentId, version, position, trigger, expectedHostId)`,
  `ResolveCodeCompletion(context, documentId, resultId, index,
  expectedHostId)` through `liveRoute` plus the completion surface, with the
  host and epoch checks; `CancelCodeCompletion(requestId)`, like
  `CancelSearch`. A new request under the same ID cancels the old one, and a
  host switch cancels them all. A canceled request returns `canceled`, also
  when a remote client returns the context error itself. Local
  `ConnectionState` reports `codeCompletion` with `liveCodeDiagnostics`.
- RPC: `completeCode` and `resolveCodeCompletion` in the live method list,
  with the ownership check; a missing position or trigger and an overlong
  result ID are refused before the backend. `codeCompletion` is advertised
  only with `liveCodeDiagnostics`. The client refuses before any work
  without the capability, and refuses answers for another document,
  version, result or item, or outside the caps (`Validate`).
- Changed from the scope: no `cancelCodeCompletion` RPC method. Canceling
  the request's context makes the client send `$/cancelRequest`, which
  cancels the server's request context and, through it, the language
  server's request. `CancelCodeCompletion` takes only the request ID: it
  ends a context of this app, whichever host it went to, and is unguarded
  in the frontend like `cancelSearch`.
- `CompletionResult.Validate` now also bounds the result ID (64 bytes, no
  control characters).
- Frontend: types (`CodeCompletionTrigger`, `CodeCompletionItem`,
  `CodeCompletionResult`, `CodeCompletionDetails`), `codeCompletion` in
  `HostCapabilities`, `api.completeCode` (a Go nil list becomes `[]`),
  `api.resolveCodeCompletion`, `api.cancelCodeCompletion` (a no-op on an old
  binding), the three names in `APP_METHODS`, and a mock that suggests the
  words of its open documents and resolves its last answer. The Wails
  bindings are generated and gitignored; `APP_METHODS` is the checked list.
