# CC-19 — Review fixes: answers stay resolvable while typing and asking again

- **Status:** ✅ Done
- **Estimate:** 3 h
- **Depends on:** CC-03, CC-10, CC-13
- **Plan:** [code-completion.md](../../plan/code-completion.md)

## Found by

A third code review of the `feature/code-completion` branch (`/code-review develop...feature/code-completion`), checked against the code before this task was written.

## Scope

- **An answer that typing overtook stays resolvable.** `Manager.Complete`
  keeps the answer for resolve only when the document is still at the
  asked version when the server answers, yet returns its `ResultID` either
  way. Typing sent during the wait (the 300 ms debounce) makes every
  resolve of that answer fail with `staleVersion`: the info panel falls
  back to listed details and a vtsls item goes in without its import. The
  answer is kept when the document is the same lifecycle (the same
  `documentState`), whatever its version; a resolve at a version still
  checks that version (`answeredAt`). An answer that is not kept is
  returned without a `ResultID`, so nothing tries to resolve it.
- **Asking again keeps the shown answer.** `beginCompletion` replaces the
  URI's kept items as soon as a request starts, while the Manager still
  names the previous answer. While a new request runs, or after it fails or
  times out, the answer on screen cannot be resolved. The session keeps the
  last answer's items until a newer answer is stored; a request in flight
  is recorded beside them, so an older request that answers later is still
  not kept.
- `keptAnswer.version`, written but never read, is removed.

## Done when

- Typing sent while the server answers leaves the answer resolvable, for
  details and, at the then current version, for extra edits.
- A new request in flight, failed or timed out leaves the previous answer
  resolvable; a newer stored answer replaces it.
- An answer for a reopened or closed document has no `ResultID`.

## Tests

- Go, fake servers (`lsp_completion_test.go`): change during the answer,
  then resolve at version 0 and at the new version; a second request held
  in the server while the first answer resolves; a second request that
  fails; a reopen during the answer gives no `ResultID`.

## Evidence

- `Manager.Complete` (`lsp_completion.go`) notes the `documentState` it
  routed to and keeps the answer when the same one is still open after the
  server answers, at any version; otherwise it clears `ResultID`.
  `keptAnswer.version` is gone.
- `keptItems` (`lsp_completion_resolve.go`) has a `pending` request ID
  beside the kept answer. `beginCompletion` only sets it;
  `keepCompletion` stores the items only for the pending request, in place
  of the kept answer; `dropCompletion` clears only the pending ID. Dropping
  an answer for the 8 MiB cap leaves the URI's request in flight pending.
- New Go tests: `TestCompletionKeptWhileAskingAgain` (a held request, one
  that fails or times out, two in flight, a closed URI),
  `TestCompletionKeptThroughTypingWhileAsked` (a change while the server
  answers, then a resolve at the new version with extra edits; a close
  while it answers gives no `ResultID`), and a pending-through-eviction
  case in `TestCompletionKeptBytesAreCapped`.
  `TestCompletionResolveKeepsTheLastAnswer` now expects the overtaken
  request's answer without a `ResultID`.
- Each new check failed with the old behaviour put back (the version
  comparison, `beginCompletion` replacing the items, eviction deleting the
  pending slot), and passes now.
- `go test -count=1 ./internal/codediagnostics/... ./internal/rpc/...
  ./internal/app/... ./internal/engine/...`: all ok. `go vet` with
  `GOOS=windows` and `GOOS=linux` on `./internal/codediagnostics/`: ok.
- Not checked: a reopen of the same document ID, which the Manager does
  not allow (an ID is never reused, so a reopen is a new ID and a new
  `documentState`); a close during the answer is tested instead. No real
  server or GUI run.
