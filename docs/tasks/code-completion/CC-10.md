# CC-10 — Import edits from resolve, on the host and the wire

- **Status:** ✅ Done
- **Estimate:** 4 h
- **Depends on:** CC-03, CC-04
- **Plan:** [code-completion.md](../../plan/code-completion.md)

## Goal

Resolving a completion item can return the extra edits (imports) the
server computes only on resolve, for the document version the editor has
now. The editor's part, which waits for these edits when an item is
accepted, is [CC-12](CC-12.md).

## Found by

CC-09's real-server QA. vtsls 0.3.0 offers `helperValue` from
`./helper.js` (label description `./helper.js`) with no
`additionalTextEdits` in the completion answer. It computes the import only
in `completionItem/resolve`: it asks tsserver for `completionEntryDetails`
and sets `additionalTextEdits` from the entry's code actions
(`@vtsls/language-service/dist/index.js`). It does this whatever
`resolveSupport.properties` the client advertises. Our resolve keeps only
`detail` and `documentation` (`lsp_completion_resolve.go`). So accepting the
item inserts `helperValue` without the import, and the file then fails to
compile.

A second problem: the host drops the kept answer at the next document
change (CC-03). A complete answer is filtered in the editor as the user
types on, and that typing is sent to the server, so by the time an item is
selected or accepted the answer is usually gone. Resolve then fails with
`staleVersion`, and the info panel falls back to the listed details.

## Design

- **The answer is kept through typing.** A document change no longer drops
  it. A new completion request, a close, a reopen or a session restart
  still does, as before. Editors resolve items of a list filtered by
  typing in the same way, and the server resolves with the document it has.
- **Resolve takes a version.** `ResolveCompletion(…, index, version)`.
  - Version 0 asks for details only, as the info panel does.
  - A version above 0 also asks for the item's extra edits. That version
    must be the document's current version, and the answering server must
    have it; otherwise the request fails with `staleVersion`.
  - The edits from the server's resolved item are checked against that
    version's text: valid UTF-16 ranges inside the text, at most 100 edits,
    and the 16 KiB text bound. Any invalid edit drops them all, since part of
    an import can break the code. An edit that overlaps an earlier one is
    dropped.
  - If the document changed while the server answered, the edits are
    dropped and the details are still returned. `CompletionDetails`
    carries `Version` and `ExtraEdits` only together.
- A server without `resolveProvider` already put its edits in the list, so
  resolve adds none.
- **Wire.**
  - The app binding, the engine, RPC (`version` in the params), the
    frontend API and the mock all carry the version.
  - `CompletionDetails.Validate` checks the edits.
  - An older host ignores the version and returns no edits, and it still
    drops the answer at a change. The editor falls back to the listed
    edits (CC-12).
- `resolveSupport.properties` stays `[documentation, detail]`. Listing
  `additionalTextEdits` would let gopls and Pyright move their edits to
  resolve too, which costs a round trip at every accept.
- Commands stay ignored. vtsls's `_typescript.applyCompletionCodeAction`
  command, used for edits it cannot express as text edits, is not run.

## Done when

- Resolving vtsls's `helperValue` at the current version returns
  `import { helperValue } from "./helper.js";` as an extra edit.
- Details resolve after typing that changed the document.
- A wrong version, a changed document, or invalid edits never return edits
  that do not fit the text.

## Tests

- Go, with fake servers: the answer survives a change and is dropped by a
  reopen or a new request; version 0 gives no edits; a version that is not
  current, or not yet sent to the server, gives `staleVersion`; the edits
  are checked against the version's text (out of range, too many, too
  long, overlapping); a change during the call drops the edits; a server
  without resolve gives none; `Validate`.
- RPC: the version and the edits cross the wire, and the client validates.
- Frontend API and mock: the version is passed through.
- Real server: CC-09's QA resolves the vtsls item at the current version and
  logs the edit.

## Done

- The kept answer survives `didChange` (`lsp_documents.go` no longer drops
  it). A newer answer, a reopen, a close or another generation still end it.
- `Manager.ResolveCompletion(…, index, version)`. A version above 0 must be
  the document's current version, and the answering route must have it;
  otherwise `staleVersion`, before the server is asked. The session gets the
  version's text and keeps the resolved item's `additionalTextEdits` only
  if all of them fit it (`resolvedEdits`). After the call, the Manager
  drops the edits if the document moved on.
- `CompletionDetails` gained `version` and `extraEdits`; `Validate` checks
  them (together or neither, at most 100, valid ranges, 16 KiB text, UTF-8,
  no overlap). The RPC client also rejects edits for a version it did not
  ask about.
- The version runs through the engine, RPC, the app binding, the frontend
  API and types, and the mock. The mock keeps its answer through changes,
  and resolving at the current version imports a name declared in another
  open document. The info panel's store asks at version 0.
- The CC-09 QA resolves an `extra` probe's item at the current version when
  its listed item has no extra edits. The TypeScript probe's `CC-10` marker
  is removed.
