# CC-23 — Review fixes: one check for completion edits

- **Status:** ✅ Done
- **Estimate:** 2 h
- **Depends on:** CC-02, CC-10, CC-13
- **Plan:** [code-completion.md](../../plan/code-completion.md)

## Found by

A third code review of the `feature/code-completion` branch (`/code-review develop...feature/code-completion`), checked against the code before this task was written.

## Scope

- The checks on completion edits (inside the text or a valid range, the
  16 KiB text bound, UTF-8, no overlap) are written out four times:
  `completionItem`, `resolvedEdits`, `validCompletionItem` and
  `CompletionDetails.Validate`. One helper takes the edits, the text's
  lines (or none, for a peer's answer) and the ranges already taken.
- Behaviour stays the same. The UTF-8 check now applies everywhere; text
  read from JSON is always valid UTF-8, so nothing is refused that was kept
  before.

## Done when

- One helper; the four callers use it; the existing tests pass unchanged.

## Tests

- Go: `go test ./internal/codediagnostics/... ./internal/rpc/...`; a direct
  test of the helper.

## Evidence

What changed:

- `validEdits(edits, lines, taken)` in `lsp_completion.go` is the one check.
  It allows at most `maxCompletionExtraEdits` edits. Each edit needs a valid
  range, inside the text when `lines` is set (a peer's answer comes without
  its text), new text of at most `maxCompletionText` bytes of UTF-8, and no
  overlap with another edit or with `taken`. It returns `taken` with the
  ranges added.
- `wireEdit` and `wireEdits` read a server's edits: they refuse an edit with
  a missing field or more than the cap, as both server-side callers did.
- Callers:
  - `completionItem` checks its main edit and its extra edits, the extra
    edits against the main one;
  - `resolvedEdits` checks the edits against the version's text;
  - `validCompletionItem` and `CompletionDetails.Validate` check edits
    without the text.
  The checks that belong to only one caller stay with it: the main edit on
  the asked line around the position, and the details' version only with
  edits.
- Behaviour: the server-side main and extra edits now also get the UTF-8
  check. Go decodes JSON strings to valid UTF-8, so nothing is refused that
  was kept before.

Tests, run on macOS:

- `go test -count=1 ./internal/codediagnostics/... ./internal/rpc/...
  ./internal/app/... ./internal/engine/...` passed, with no existing test
  changed.
- New `TestValidEdits` covers:
  - inside and past the text, with and without it;
  - a column after or inside a surrogate pair;
  - backwards and negative ranges;
  - text at and over the cap, and invalid UTF-8;
  - overlaps with each other, two edits at one place, edits side by side,
    and an overlap with the main edit;
  - edit counts at and over the cap;
  - the returned `taken`;
  - for `wireEdits`: none, whole, a missing range or text, and over the
    cap.
- With the overlap check removed from `validEdits`, the existing tests of
  all four callers fail:
  - `TestCompletionAgainstFakeServer`;
  - `TestCompletionResolveAgainstFakeServer`;
  - `TestCompletionResultValidate`;
  - `TestCompletionDetailsValidate`;
  - in rpc, `TestCompletionClientRefusesBadAnswers`.
  With the text check removed, the two fake-server tests fail.
- `GOOS=windows` and `GOOS=linux` `go vet` on codediagnostics and rpc
  passed; `gofmt -l` lists none of these files.

Not checked: the frontend, which this task does not change.
