# FS-08 — Session text size and scroll position

- **Status:** ✅ Done
- **Estimate:** 3 h
- **Depends on:** FS-02, FS-03
- **Plan:** [font-settings.md](../../plan/font-settings.md)

## Scope

- `TranscriptView.svelte`: set `--session-font-size` on
  `.messages-scroll-area` from `preferences.sessionFontSize` (nothing for the
  default). Since FS-01 and FS-02 size every session role from that body,
  all session text follows with its ratio. Print and other places that render
  parts outside the scroll area keep the default.
- Scroll on change: a transcript following the bottom stays at the bottom;
  otherwise the first visible message stays in place. Session find
  highlights repaint.

## Likely files

`components/transcript/TranscriptView.svelte`,
`frontend/test/transcript*.test.mjs`.

## Acceptance criteria

- Default: no property is set; sizes equal FS-02's defaults.
- At 11 and 24 px every session role keeps its ratio to the body.
- Following and scrolled-up transcripts keep their place when the size
  changes.

## Tests

Unit test for the scroll-keeping logic; SSR check of the style property with
and without the setting.

## Outcome

- `TranscriptView.svelte`: when a session size is chosen, `.messages-scroll-area`
  gets `style:--session-font-size` from `sessionFontVar(preferences.sessionFontSize)`.
  At the default it sets nothing. Print and other places outside the scroll
  area keep the 14.5px fallback.
- New `transcriptAnchor.ts`:
  - `firstVisibleMessage(container)` gives the index of the first message
    whose bottom is below the top of the view, how far its top is from the
    view's top, and its height. `topMessageIndex()` now uses it.
  - `restoreMessage(container, anchor)` scrolls back to that message. If it
    started in view, its top goes back to the same place. If it started above
    the view, the same share of it is above the view again.
- Size change, scrolled up: an `$effect.pre` records the first visible
  message before the new size renders, and an `$effect` puts it back
  afterwards.
- Size change while following or anchored to the bottom: nothing is recorded.
  The existing `ResizeObserver` keeps the end in view as the text grows.
- Session find needs no repaint. Its matches are `<mark>` elements in the
  text, so they resize with it.
- These stay at their fixed rem sizes: the "End of transcript" marker,
  "Load earlier messages" and the empty-transcript notice. They are view
  controls and notices rather than message text, as the plan scopes it.
  Moving them onto the ratios would change their default size by more than
  1px (the root is 18px), so that choice goes to the user in FS-09.

## Evidence

- New `test/transcript-font-size.test.mjs` (6 tests):
  - 4 unit tests for `transcriptAnchor`, using a fake scroll container:
    - picking the first visible message, including at a boundary;
    - keeping a message's top in place when the text is scaled ×1.5 and
      ×0.75;
    - keeping the same 30% of a message above the view;
    - doing nothing when the message is gone.
  - An SSR render of `TranscriptView` (imports stubbed): the scroll area has
    no `style` at the default, `--session-font-size: 18px;` at 18 and
    `11.5px` at 11.5.
  - A source check that the anchor is taken only when not following, and
    put back after the size renders.
- `npm test`: 1122 tests, 1121 pass, 0 fail, 1 skipped. `npm run check`:
  0 errors, 0 warnings. `npm run build`: passes. `git diff --check`: clean.
- Browser check (Vite dev server, Chromium, mock sessions plus the FS-02
  fixture message):
  - Every text node in the scroll area of all 4 sessions (113) was measured
    at 14.5, 24 and 11px. At 24 and 11px, each one was its default size ×
    24/14.5 and × 11/14.5, within 0.02px. The one exception is the "End of
    transcript" marker, which stays at 12.96px.
  - In a session made longer (64 messages), scrolled halfway, the size went
    14.5 → 24 → 11 → default. Message 40 stayed first each time, with 5.3%,
    5.3%, 5.9% and 5.3% of it above the view.
  - Scrolled to the bottom, the view stayed at the bottom (0px left) at 24
    and 11px.
  - The same results came with Chromium's CSS scroll anchoring turned off
    (`overflow-anchor: none`). WebKit has no CSS scroll anchoring.
  - With the restore turned off as a check, the first message became 33 at
    24px and 44 at 11px, so the restore is needed.
  - I also looked at a screenshot at 11px.
- Not checked: the Windows and macOS apps, and a transcript that grows
  while the size changes. Those go to FS-09.
