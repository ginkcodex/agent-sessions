# IR-07 — Attribute scrolling and native-window compositing cost

- **Status:** 🟡 Partial — user reports 0% idle GPU after opacity change; controlled GPU A/B and visual QA outstanding
- **Estimate:** 3 h
- **Depends on:** IR-06
- **Plan:** [idle-rendering.md](../../plan/idle-rendering.md)

## Scope

Investigate the user-reported 50–60% GPU spikes when scrolling workspace/session lists or older transcripts with the terminal closed. Separate application painting from system composition. Inspect native window opacity and test it as a hypothesis, without assuming that high presentation rate alone is a defect.

## Likely files

QA record, macOS window integration in cmd/agent-sessions if an experiment is justified; shared scroll components only if measurements implicate them. Do not edit the Go module cache or change display settings as a substitute for an app fix.

## Acceptance criteria and tests

- Record process GPU execution intervals, display presentation rate, display scaling and workload limitations.
- Compare idle and scrolling with a repeatable pane/workload, including a comparable WebKit baseline where practical; do not treat an uncoordinated capture as a controlled A/B.
- If testing native opacity, compare the existing non-opaque window with an opaque native window and opaque backing color, using public AppKit APIs on the UI thread. Verify light/dark appearance, resize, fullscreen, file-drop overlay and window lifecycle. No dependency cache edits, private APIs or installed-app replacement.
- Record actual results, including no improvement; keep Windows/Linux behavior unchanged.
- Approved experiment uses adaptive AppKit window backing color and an opaque flag on main windows only, with `AGENT_SESSIONS_MACOS_OPAQUE=0` to retain the original configuration for same-binary A/B. Default enables the experiment; no persisted setting. Test switch parsing, wiring, nil native handle, actual AppKit opacity/backing color in light/dark appearance and non-macOS compilation.

## Evidence

2026-11-11: User reports scrolling any of the three panes triggers 50–60% GPU use even with the terminal closed. Read-only captures from the running installed app (PID 63471; WebContent 63476) are in `/tmp/as-scroll-gpu.1LOQQ5/`, temporary/local only.

- In `scroll-coordinated.trace`, seconds 9–10 contain 111 and 120 display surface swaps; summed WindowServer GPU intervals occupy about 65% of each second (all recorded GPU channels, not the device utilization counter). WebKit GPU intervals remain low.
- In `scroll-then-rest.trace`, WindowServer fragment intervals total 9.643 s over about 30 s, with all-channel one-second sums reaching about 69%. Display surface-swap buckets reach 118–119/s during several bursts. WebKit fragment and vertex intervals total 0.237 s. Ghostty and Chrome also contribute GPU work, so these are system-wide observations, not app-isolated measurements.
- Despite capture filenames, no manual scroll/rest schedule was communicated or confirmed, and no UI automation drove a gesture. Bursts cannot be assigned to a specific pane or gesture. No before/after opacity measurement was made.
- A separate 5 s WebContent sample spends 3,452 of 3,550 main-thread samples waiting for messages; it was not synchronized to the high-load burst. It does not rule out CPU work during individual scrolls.
- Display report: Apple M5, built-in display at 120 Hz; reported scaled raster 3600×2338, logical 1800×1169 and physical panel 3024×1964. Runtime sample confirms the installed universal app executes ARM64, not Rosetta. `go version -m` on the universal file alone reports the first (amd64) slice and must not be used to infer runtime architecture.
- Wails v3.1.0 source initializes NSWindow with clear background and `opaque = NO`; the app omits BackgroundColour, so the later setter keeps alpha zero and the Normal backdrop does not restore opacity. The normal WKWebView path does not explicitly make WebKit transparent. This is a source-level hypothesis, not a live opacity query or causal diagnosis. See the QA record for upstream source references.
- The initial investigation changed no rendering source and did not build/launch/replace the app or change display settings. Controlled native opacity A/B was not run.

### Approved implementation

2026-11-11: Added a main-window runtime-ready hook. macOS resolves the native handle on Wails' UI thread, sets AppKit's adaptive `windowBackgroundColor` and then `opaque = YES`. About, WKWebView/child layers, titlebar, shadows, window alpha and display settings are untouched. Non-macOS integration is a no-op. `AGENT_SESSIONS_MACOS_OPAQUE=0` skips the helper and preserves Wails' original configuration for same-binary A/B; unset or `1` enables it. This is an experimental default; the subsequent user idle observation is recorded below, separately from controlled measurement.

- `go test -tags 'desktop,production' ./cmd/agent-sessions -count=1`: **passed**. Includes switch tests and an executable Objective-C fixture using the actual helper against an unshown NSWindow, on the process main thread. Checks nil handle, opaque flag/backing color in Aqua and Dark Aqua, repeat calls, retained child views/style/shadow/alpha. This is property validation, not a launched WKWebView app or visual QA.
- Initial fixture compile failed because ARC required an explicit bridged pointer cast; fixed with `__bridge`, then the desktop package tests passed.
- `go vet -tags 'desktop,production' ./cmd/agent-sessions`: **passed**.
- macOS ARM64 desktop production build: **passed**, output `/tmp/as-opacity-build.4HuxJq/agent-sessions` (version ldflag 1.4.0, includes uncommitted changes). Final build used packaging's macOS 12 target/compiler/link flags; duplicate `-lobjc` linker warning remains. This bare executable is not a complete replacement app bundle.
- Windows desktop test **cross-compilation passed**, not native execution. Linux native build/runtime not checked; its opacity hook is a no-op.
- `make test` (`go test -race ./...`): **passed**, some package results cached. This default suite excludes desktop-tagged integration; the tagged desktop tests above cover that separately. Docker SSH integration and native Windows/Linux execution were not enabled. Frontend tests were not rerun for this native-only step; prior IR-06 results remain above.
- `git diff --check`: **passed**. Editor go-list warnings arise from the `desktop`/OS build tags; tagged build/test commands above validate the selected files without changing editor configuration.
- During implementation, no installed-app replacement, app relaunch or controlled GPU comparison was performed by the assistant. The native fixture does not establish actual WKWebView appearance or resize/fullscreen/drop handling.
