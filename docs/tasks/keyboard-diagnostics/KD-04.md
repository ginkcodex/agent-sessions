# KD-04 — Desktop check and fault analysis

- **Status:** 🟡 Partial (a fault log was saved and analysed; there is no healthy log from the app to compare it with, and the terminal was not recorded)
- **Estimate:** 2 h
- **Depends on:** KD-02, KD-03
- **Plan:** [keyboard-diagnostics.md](../../plan/keyboard-diagnostics.md)

## Scope

Build the macOS app locally and turn on Record Keyboard Events. Type Vietnamese
with OpenKey in a page field and in the terminal, then save a log. Check that
OpenKey's Backspace and `â` show up as native and page records. Keep the build
running until the fault returns, save a log while it is present, and compare
the two logs against the questions in the plan.

## Acceptance criteria

- A healthy log shows OpenKey's synthetic events (source PID and key code 0)
  reaching both AppKit and the page.
- A fault log is saved and analysed, and the finding is recorded here. A fix,
  if any, becomes its own task.

## Evidence

- **Log.** `~/Library/Logs/agent-sessions/keyboard-20261116-232345.jsonl`,
  saved by the user from app 1.6.9 while the fault was present. It holds 1102
  records (765 page, 335 native, 2 markers) and none were dropped.
  - Header: the window's input context and TIS both have ABC selected, the
    first responder is WKWebView, Secure Event Input is off, and there is no
    marked text. The context also has Apple's Vietnamese and VNI enabled.
  - Every page record targets the chat composer (`textarea.svelte-oq8dxb`)
    in one window.
- **Phase 1 (23:23:22–26).** Only hardware keys (PID 0, state ID 1). `cong965`
  reached the page as typed, with no OpenKey events. OpenKey probably gave up
  on the word after the `9`. The user then pressed Cmd+A and Backspace.
- **Phase 2 (from 23:23:27.7).** OpenKey's events (PID 13235, private state
  ID 114723506) reach AppKit in the right order. For `cong6`:
  U+202F spacer, 4× Backspace (key code 51), then `ông` (U+00F4 U+006E
  U+0067, key code 0).
- **The page gets the same events in a different order.** Within one
  millisecond: keydown and keyup for the spacer, the 4 Backspace keyups,
  keydown and keyup for `ông`, and only then the 4 Backspace keydowns. The
  input events follow the same order: `insertText " "`, `insertText "ông"`,
  then 4× `deleteContentBackward`. The deletes remove the text just
  inserted, so each word looks unconverted. In later words some Backspace
  keydowns come before the text and some after.
  - `bursts.py` (a throwaway script) found that 18 of the 19 replacements in
    the log had 1 to 4 Backspace keydowns after the replacement text.
  - Rebuilding the text from page input events gives
    `cong96cong hoa xa hoi chu nghia Viet Nam, doc lap tu do hanh phuc`.
    Rebuilding it from the native order gives
    `cộng hòa xã hội chủ nghĩa Việt Nam, độc lập tự do hạnh phúc`.
- **Verdict.** The log matches none of the plan's four cases. OpenKey works,
  AppKit gets its events, and the page gets all of them, but WebKit
  dispatches the Backspace keydowns after the replacement. Keyups skip the
  input context and keydowns do not, so the likely cause is WebKit's
  input-context step finishing out of order in this process. This is
  inferred from the order, not proven.
- **WebKit source** (`Source/WebKit/UIProcess/mac/WebViewImpl.mm` on WebKit
  main, read on 2026-11-16; the WebKit in macOS 27.2 may differ).
  `keyDown`, `keyUp` and `flagsChanged` all call `interpretKeyEvent`, which
  passes each event to `-[NSTextInputContext handleEventByInputMethod:completionHandler:]`
  and sends it to the page only from the completion. The page's order is
  therefore the order in which those completions return. Main also has a
  "correct key event order" mode (a queue for keydowns and a holding tank for
  keyups), which is off for some input sources such as Apple's Simple Telex.
  Native text views and Chromium have no such asynchronous step, which fits
  "only this app". What makes the completions return out of order only
  sometimes is still unknown.
- **Baseline.** A Swift harness (a plain WKWebView, the same burst sent as
  NSEvents in one run-loop turn) kept the order and gave `công`, three runs
  out of three. Posting the burst as CGEvents could not be tried: CGEvents
  posted to the harness did not arrive in this session, even for plain keys.
- **Not checked.**

  - The terminal while the fault is present.
  - What puts the process into this state; the log starts after the fault
    began.
