# LR-02 — Spike: redirects and signatures

- **Status:** ✅ Done. The key type changed: v4 EdDSA (legacy Ed25519) for both keys; RFC 9580 Ed25519 fails on Ubuntu 24.04 and Fedora 40
- **Estimate:** 3 h
- **Depends on:** LR-01
- **Plan:** [linux-repos.md](../../plan/linux-repos.md)

## Scope

Check the assumptions the plan rests on, with a throwaway repository on the
LR-01 preview Worker and a test key:

- apt (Ubuntu 24.04, Debian 13, newest Ubuntu) and dnf (Fedora 40, newest
  Fedora) download a package through a 302 from our domain to a GitHub
  release asset, and on to GitHub's file host.
- An `InRelease` clear-signed by `openpgp` with an Ed25519 key verifies with
  `gpgv` and with `sqv` (newer Ubuntu), and `repomd.xml.asc` with dnf's
  `repo_gpgcheck=1`.
- nfpm signs an RPM with an Ed25519 key and Fedora 40's `rpm -K` accepts it.
  If not, the RPM key is RSA 4096 (the plan's default).

## Acceptance criteria and tests

- Each check recorded with the container, command and output.
- Any failed assumption updates [linux-repos.md](../../plan/linux-repos.md)
  before LR-08 or LR-11 starts.

## Result

| Assumption | Result |
|---|---|
| apt follows a 302 from our domain to the GitHub asset | ✅ apt 2.8.3 (Ubuntu 24.04), 3.0.4 (Debian 13), 3.3.3 (Ubuntu 26.10) |
| dnf follows it | ✅ dnf 4.22 (Fedora 40), dnf5 5.4.6 (Fedora 45) |
| openpgp.js Ed25519 `InRelease` and `Release.gpg` verify with `gpgv` and `sqv` | ✅ with a v4 **EdDSA (algorithm 22)** key. ❌ with RFC 9580 Ed25519 (algorithm 27): `gpgv` 2.4.4 answers `ERRSIG` |
| `repomd.xml.asc` passes `repo_gpgcheck=1` | ✅ with EdDSA on Fedora 40 and 45. ❌ RFC 9580 Ed25519 on Fedora 40: "No binding signature at time …" |
| nfpm signs an RPM with Ed25519 and Fedora 40's `rpm -K` accepts it | ✅ with EdDSA, on Fedora 40 (rpm 4.19.1.1) and 45 (rpm 6.1.0). RFC 9580 Ed25519: Fedora 40 refuses the key |

So both keys are v4 EdDSA keys, what `gpg --quick-gen-key … ed25519`
makes; openpgp.js makes them with `{type: 'ecc', curve: 'ed25519Legacy'}`
(its `type: 'curve25519'` is the RFC 9580 kind). The plan's Keys section
now says so; the RPM key is no longer RSA 4096.

Other findings for later tasks:

- Ubuntu 24.04 verifies with `gpgv` 2.4.4; Debian 13 (sqv 1.3.0) and
  Ubuntu 26.10 (sqv 1.4.0) with `sqv`. Neither printed a policy warning for
  the EdDSA key.
- apt fetched `Packages` through `by-hash/SHA256/…` (`Acquire-By-Hash: yes`)
  on all three, and fell back to `Release` + `Release.gpg` when `InRelease`
  was missing.
- `signed-by=` takes the binary key (`.gpg`) and the armored one (`.asc`)
  alike on all three.
- openpgp.js 6.3.2 signs with SHA-512 and adds a
  `salt@notations.openpgpjs.org` notation; every verifier accepted both.
- Fedora 40's dnf 4 `makecache` exits 0 when the repository's signature
  fails ("Ignoring repositories: agent-sessions"). LR-16 must check the
  output, or install, not the exit code. `dnf download` needs
  `dnf-plugins-core` there.
- Fedora's `rpm -i` refuses a tampered RPM on both versions; rpm 6 reports
  the signature as BAD, rpm 4.19 the payload digest.

## Evidence

Run on 2026-11-14 on macOS arm64 with OrbStack, so every container is arm64
and downloads the `arm64`/`aarch64` 1.5.5 packages. Workspace
`/tmp/lr02.SeHuZh`, removed afterwards.

**Setup**

- Keys: openpgp.js 6.3.2 in Node 24. Two throwaway signing keys, `legacy`
  (EdDSA, algorithm 22, fingerprint B5C7ADC1…432BBABA) and `rfc9580`
  (Ed25519, algorithm 27, E0FA18F0…6194E0D2), plus an RSA 4096 key for
  comparison.
- Repositories, per key:
  - apt: `dists/stable/main/binary-{amd64,arm64}/Packages{,.gz}` from 1.5.5's
    `repo-meta.json` (LR-09), by-hash copies, a `Release` with
    `Acquire-By-Hash: yes`, `InRelease` (clear-signed) and `Release.gpg`
    (detached, binary signature type).
  - dnf: the repodata from `assemble-rpm-repo.sh` (LR-10) and
    `repomd.xml.asc` (detached).
  - Copies: `-detached` (no `InRelease`) and `-tampered` (one line of
    `InRelease` and the `<revision>` of `repomd.xml` changed after signing).
- Server: a 40-line Node server in a `node:22` container on a private
  Docker network (`http://lr02-srv:8080`). Static files, and a 302 for
  `*/pool/<version>/<file>` to
  `https://github.com/ginkcodex/agent-sessions/releases/download/v<version>/<file>`,
  as the Worker will answer. GitHub answers that with a 302 to
  `release-assets.githubusercontent.com`.
- apt, per container and key: `apt-get update` with only this source
  (`-o Dir::Etc::sourceparts=-`, `-o Debug::Acquire::gpgv=1`), then
  `apt-get download agent-sessions`, then `sha256sum`. `ca-certificates`
  was installed first: the base images lack it, and the first run failed
  on GitHub's certificate for that reason.
- dnf, per container and case, in a new container: an `as.repo` with
  `gpgcheck=0`, `repo_gpgcheck=1` and `gpgkey=` the served key;
  `dnf -y makecache`, then `dnf download agent-sessions`.
