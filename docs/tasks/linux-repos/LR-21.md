# LR-21 — Ship the repository keyring in the .deb

- **Status:** ⬜ Not started (needs the maintainer's decision; see Questions)
- **Estimate:** 3 h
- **Depends on:** LR-15 (the real repository key)
- **Plan:** [linux-repos.md](../../plan/linux-repos.md)

Found during LR-15. apt checks `Release` against the keyring that users
downloaded once, into `/usr/share/keyrings/agent-sessions.gpg`, and never
fetches it again. So both a renewal and a rotation reach apt users only if
they fetch the keyring again by hand:

- **Renewal.** A copy past its old expiry date is refused, even though the
  served key was extended. This was seen with gpgv 2.4.4, sqv 1.3.0 and
  sqv 1.4.0.
- **Rotation.** Dropping the old key breaks apt for everyone who has not
  fetched the keyring again.

dnf has no such problem: it fetches the key file again by itself.
See [linux-repos-keys.md](../../plan/linux-repos-keys.md).

## Scope

Debian's own archive keyrings, and many vendors, solve this by shipping the
keyring in a package. Then `apt upgrade` delivers a renewed or rotated key
before the old one stops working.

- Add the public keyring to the repository, as
  `packaging/linux/agent-sessions.gpg`. It is the binary keyring that the
  Worker serves at `/apt/agent-sessions.gpg`.
- In `packaging/nfpm.yaml`, install it into the `.deb` only, at
  `/usr/share/keyrings/agent-sessions.gpg`, which is the path the install
  steps use.
- Add a check, in CI or in the release job, that every key the site serves
  is in the packaged keyring. Otherwise a rotation could ship a package
  without the new key.
- Update the keys procedure:
  - a renewal or rotation updates this file first, in a release made before
    the site changes;
  - users who upgrade in that window get the new key without doing anything.

## Questions for the maintainer

- The plan says that "packages do not add the repository on install".
  Shipping only a keyring does not add a source, but it does write a file
  that the install steps tell users to create themselves. Is that
  acceptable?
- `apt remove agent-sessions` would delete the keyring, while the user's
  `.list` file stays. `apt update` then fails for that source until the user
  removes it. Is that acceptable? The alternative is a separate keyring path
  that the install steps point `signed-by=` at.
- Should it be a separate `agent-sessions-archive-keyring` package, as
  Debian does? That needs a second package per release, but removing the app
  would leave the keyring in place.

## Acceptance criteria and tests

These need the real key, or a throwaway key on a preview. Run them in
Ubuntu 24.04, Debian 13 and Ubuntu 26.10 containers:

- A user who followed the install steps upgrades to a release that ships the
  keyring. dpkg replaces the downloaded file without asking, and
  `apt update` still passes.
- A renewal shipped this way: after the old expiry date, `apt update`
  passes with no manual step.
- A rotation shipped this way: once the old key is dropped, `apt update`
  passes with no manual step.
- `make package-linux` puts the keyring in the `.deb` and not in the `.rpm`.
