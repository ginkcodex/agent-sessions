# LR-08 — Sign RPMs in CI

- **Status:** ✅ Done (the first run on GitHub Actions is part of LR-19)
- **Estimate:** 2 h
- **Depends on:** LR-02, LR-15
- **Plan:** [linux-repos.md](../../plan/linux-repos.md)

## Scope

As planned:

- `packaging/nfpm.yaml`: `rpm.signature.key_file` from an environment
  variable, with its passphrase from nfpm's environment variable.
- The release workflow's linux job writes the key from the secret to
  `$RUNNER_TEMP`, signs, and removes it. Without the secret (forks, manual
  runs) RPMs stay unsigned, with a warning; a publishing run fails instead.
- `packaging/linux/verify-packages.sh` imports the public key and checks
  `rpm -K` in a Fedora container when a key is given.

### Decision: sign in the release jobs with rpmsign, not in the build with nfpm

The RPMs are signed in the two jobs that gather the release set, `artifacts`
(manual runs) and `release`, by a new `packaging/linux/sign-rpms.sh`. Both
jobs already run in the `release` environment, which holds `MINISIGN_KEY`.
Signing there rather than in the `linux` jobs:

- **Keeps the key away from the build.** The `linux` jobs run `npm ci`, the
  frontend build and Go code. They would need the key on two runners (amd64
  and arm64), outside the protected environment.
- **Signs once, after every check.** The `linux` jobs' checks
  (`verify-packages.sh`, the `.deb` install) run on the unsigned packages as
  before.
- **Puts every signature in one place.** The release's signatures (minisign
  and RPM) are both made in that environment.

`repo-meta.json` and `SHA256SUMS` are written after signing, so both
describe the signed files.

`sign-rpms.sh` checks each signature against a database holding only that
key, so `verify-packages.sh` is unchanged. `rpm -K` exits 0 for an unsigned
package too, so the script looks for the signature line itself. The Fedora
check runs here and in [LR-16](LR-16.md) rather than in the release job.

## Done

- `packaging/linux/sign-rpms.sh <dir>`:
  - It reads `RPM_SIGNING_KEY`, one armored secret key without a passphrase
    (as `repo-keys.sh secret` writes it), into a GnuPG home made for the
    run.
  - It refuses the following: no key, more than one secret key, a public key
    only, a key that cannot sign now (expired or revoked), anything gpg
    cannot import, and a directory with no `.rpm`.
  - It signs every `.rpm` with `rpmsign --addsign`. `__gpg` is set because
    Ubuntu's rpmsign looks for gpg in `/usr/bin`.
  - It checks each package against a database holding only that key. It
    needs `Signature, key ID <last 8>: OK` (rpm 4) or
    `signature, key fingerprint: <fingerprint>: OK` (rpm 6), not just the
    exit code.
  - It removes its temp dir and stops its gpg-agent.
- `.github/workflows/release.yml`:
  - `artifacts` and `release` install `rpm` too.
  - A new "Sign the .rpm packages" step comes before "Write repo-meta.json".
  - With `publish` true and no `RPM_SIGNING_KEY`, the step stops with
    `::error::`. On a manual run it gives `::warning::` and leaves the
    packages unsigned.
  - The header comment names the secret.
- Found while testing:
  - rpm 4.19 does not update an imported key, so an extended RPM key fails
    on Fedora 40 after the old expiry date. `repo-keys.sh extend` now
    refuses RPM keys, and `show` says "make its successor by" for them.
  - The keys doc says that an RPM key is rotated, never extended.
- `docs/plan/linux-repos.md` (In CI) and `docs/plan/linux-repos-keys.md`:
  - where the signing happens;
  - `gh secret set RPM_SIGNING_KEY --env release`;
  - the RPM rotation rule;
  - a new "RPM signatures (LR-08)" results table.

## Evidence

**sign-rpms.sh in Ubuntu 24.04 (rpm 4.18.2, gpg 2.4.4)**

The packages were the two v1.5.6 release `.rpm` files from GitHub, signed
with the LR-15 throwaway RPM key (`…FB9A5B5F306C3B25`).

- Both were signed and checked, with exit 0. Their SHA-256 changed, and
  their `PAYLOADDIGEST` was unchanged.
- No temp entry or gpg-agent was left.
- Running it again on signed files exits 0: rpmsign says "already contains
  identical signature, skipping".
- Failure cases, each exit 1 with its own message:
  - no key;
  - an empty dir;
  - two secret keys;
  - a public key only;
  - an expired key ("cannot sign");
  - `garbage`;
  - a truncated `.rpm` ("not signing corrupt package").

**The same script on Fedora 45 (rpm 6.1.0 with rpm-sign)**

It signed and checked the x86_64 package, taking the rpm 6 "key fingerprint"
path.

**The workflow step's shell, run in Ubuntu 24.04**

| Case | Exit | Output |
|---|---|---|
| `PUBLISH=true`, no key | 1 | `::error::` |
| `PUBLISH=false`, no key | 0 | `::warning::` |
| `PUBLISH=true`, key | 0 | signed and checked |

**Signed packages on Fedora 40 (rpm 4.19.1.1) and 45 (rpm 6.1.0)**

The full table is in
[linux-repos-keys.md](../../plan/linux-repos-keys.md#rpm-signatures-lr-08).

- `rpm -K` reports `OK` once the key is imported.
- A payload changed after signing gives `BAD`, with exit 1.
- Fedora 45's rpm refuses to install an unsigned package (v1.5.6 as
  released: "does not verify: no signature"), or one whose key is not
  imported.
- dnf installs local files either way.

**Expiry, with key E (expired 2026-11-12)**

- A package signed while E was valid verifies with the expired copy and with
  the extended key, on both Fedora versions.
- A package signed after the extension is `NOTTRUSTED` with the expired copy.
- `rpm --import` of the extended key fixes that on rpm 6.1, but not on
  rpm 4.19: the import exits 0 and keeps the old copy.

**repo-keys.sh, in Ubuntu 24.04**

- `extend` refuses an RPM key, with exit 1, and still extends a repository
  key.
- `show` prints "make its successor by" for the RPM key.

**Lint**

- `shellcheck` is clean on `sign-rpms.sh` and `repo-keys.sh`.
- `actionlint` on `release.yml` reports only an SC2046 warning in the macOS
  keychain step, which was already there at HEAD.
