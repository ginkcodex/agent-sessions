# LR-05 — Ingest endpoint

- **Status:** ✅ Done. Ran on the `develop` preview against `agent_sessions_demo`; production waits for LR-19
- **Estimate:** 3 h
- **Depends on:** LR-04
- **Plan:** [linux-repos.md](../../plan/linux-repos.md)

## Scope

`POST /api/ingest {"tag": "..."}`:

- Requires `Authorization: Bearer $INGEST_TOKEN`, compared in constant time.
- Reads the release through LR-04 and writes `releases`, `assets` and
  `release_documents` in one transaction.
- Same `SHA256SUMS` and prerelease flag as stored: no-op,
  `200 {"changed": false}`. Either different: replace the release's rows,
  `{"changed": true}`.
- After a change, runs the rebuild hook (a no-op until LR-14). A hook
  failure is reported in the response and logged; the records stay.

## Likely files

`web/src/server/ingest.ts`, `web/src/worker.ts`, tests.

## Acceptance criteria and tests

Against the local Postgres with a fake GitHub:

- Missing or wrong token: 401, nothing written.
- First ingest writes the rows; the second is a no-op; a changed
  `SHA256SUMS`, or a release turned into a pre-release, replaces them.
- A failure halfway (GitHub error after the first asset) leaves no rows.

## Done

In `agent-sessions-web`, branch `feat/linux-repos`, commit `17cc694`:

- `worker/ingest.ts`:
  - `writeRelease(sql, record)`: one transaction, under a transaction-level
    advisory lock so concurrent ingests of a new release cannot both insert
    it. When the stored `sha256sums` and `prerelease` are the same it
    returns `false` and writes nothing; otherwise it deletes the release
    (assets and documents cascade) and inserts the release, every asset and
    `repo-meta.json`.
  - `ingest(sql, github, tag)`: LR-04's `readRelease`, which finishes every
    GitHub read before anything is written, then `writeRelease`.
  - `handleIngest`: POST only (405); 503 while `INGEST_TOKEN` is not set;
    `Authorization: Bearer` compared through SHA-256 digests with a
    constant-time loop (401 with `WWW-Authenticate: Bearer`); body exactly
    `{"tag": "<string>"}`, at most 1 KB (400). Answers 200
    `{"version", "changed"}`; 400 for a bad tag, 404 for no such release,
    422 with the reason when the checks refuse it, 502 for other GitHub
    errors, 503 with `Retry-After` when rate limited, 500 `database error`
    with no details. Everything is `no-store`.
  - After a change it calls the rebuild hook (a no-op until LR-14). If the
    hook throws, the answer is 500 with `changed: true` and "rebuild failed;
    the release is recorded", and the error is logged. The release workflow
    sees the failure; the rows stay.
- `worker/index.ts` routes `/api/ingest`, with `INGEST_TOKEN` and
  `GITHUB_TOKEN` as Worker secrets and a database client per request,
  ended in `ctx.waitUntil`.
- `.gitignore` ignores `.dev.vars`; the README lists the two secrets, how to
  set them for production and previews, and a local ingest call.

Found along the way: since an unchanged release is a no-op, re-ingesting
does not retry a failed rebuild. LR-06's cron now also runs the rebuild
every hour (LR-14 makes it stop early when its inputs are unchanged).

  tests), against the compose Postgres 17 with a fake GitHub serving the
  real 1.5.5 release fixture.
  - No token, an empty one, a wrong one, one with a character more or less:
    401 each, nothing written. No `INGEST_TOKEN`: 503. GET: 405.

    rebuild hook ran once in all.

    reason, nothing written.

    rows on a first write; with a release already stored, the stored rows
