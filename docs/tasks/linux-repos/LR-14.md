# LR-14 — Worker: generations, rebuild and serving

- **Status:** 🟡 Partial: built and checked locally; the CPU time on the preview deployment is not measured yet (the maintainer chose to measure it on production after the first release, LR-19, rather than give the preview a key)
- **Estimate:** 3.5 h
- **Depends on:** LR-05, LR-11, LR-12, LR-13
- **Plan:** [linux-repos.md](../../plan/linux-repos.md)

## Scope

- The rebuild hook for ingest: build apt and dnf files from every stable
  release with `repo-meta.json`, sign, write a new generation in one
  transaction, then point `current` at it. Prune generations beyond the
  newest five and older than 14 days.
- Routes as in the plan's serving table, with its cache headers. Pool paths
  redirect only to assets in the `assets` table.

## Likely files

`web/worker/repo/generation.ts`, `web/worker/repo/routes.ts`, tests.

## Acceptance criteria and tests

Against the local Postgres:

- After two ingests, a hash-named file from the first generation is still
  served.
- A rebuild that fails during signing leaves `current` unchanged, and a
  missing or invalid `REPO_SIGNING_KEY` (LR-13's `SigningKeyError`) is
  logged with its reason while the current generation stays served.
- `/rpm/agent-sessions.repo` comes from `repoFile(origin)` per request.
- An unknown pool path is 404; a known one is a 302 to its GitHub URL.
- A release turned into a pre-release drops out of the next `Packages` and
  `primary`.

On the preview deployment:

- The CPU time of an ingest with a full rebuild, from the Worker's
  observability logs (moved here from LR-01, which measured only local
  workerd). Above about 5 ms, the plan moves to Workers Paid.

## Done

Web commit `b8c338d` (`agent-sessions-web`, branch `feat/linux-repos`):

- `worker/repo/generation.ts`: `rebuildRepositories` lists the stable
  releases that have a `repo-meta.json`, loads the keys, and hashes the
  inputs (`BUILD_FORMAT`, each release's meta, the key fingerprints and
  `RPM_PUBLIC_KEYS`). With the same inputs as the current generation it stops
  there and does not sign. Otherwise it builds and signs every file, then in
  one transaction (under an advisory lock, with the inputs checked again)
  inserts the generation and its files, points `repo_state.current` at it,
  and prunes generations that are both older than 14 days and outside the
  newest five. A missing or unusable key throws `SigningKeyError` before
  anything is written.
- `worker/repo/routes.ts`: `handleRepo` for `/apt/*` and `/rpm/*` as in the
  plan's serving table: hash-named files from any kept generation
  (immutable, one year), other index files from the current generation
  (5 min), key files and `.repo` (1 h), pool paths as a 302 to the recorded
  GitHub asset of the right kind (1 day), 404 for 60 s. ETag (the sha256)
  and Last-Modified give 304s; HEAD has no body; other methods get 405. The
  Cache API keys on origin and path. A database error is 503 with
  `Retry-After: 60` and `no-store`.
- `worker/index.ts`: ingest and the hourly cron call the real rebuild and log
  `rebuild: wrote|unchanged, generation N, M releases`; the router sends
  repository paths to `handleRepo` before the static assets.

## Evidence

- `npm run test:db`: 37 pass, 10 of them new in `worker/test/db/repo.test.ts`,
  covering each acceptance criterion against the local Postgres:
  - two ingests: the first generation's hash-named files are still served,
    byte for byte, as immutable;
  - a sign failure, and an undefined, garbage or public-only key, each
    reject and leave `current` and the generation count unchanged; the next
    good rebuild catches up;
  - `.repo` has `baseurl=https://repo.example/rpm` for that origin;
  - unknown pool paths, an `.rpm` under `apt/`, `repo-meta.json`, a
    traversal and an unknown by-hash name are 404; known `.deb` and `.rpm`
    are 302 to their GitHub URLs;
  - a release turned pre-release drops out of `Packages` and `primary`;
  - pruning with eight generations keeps the young one plus the newest five;
  - the signatures verify with openpgp.js; cache, 503, HEAD, 304s and 405.
- Mutation checks, one at a time on a copy: pruning the newest, hash-named
  files only from the current generation, ignoring the pool kind, no inputs
  check, no pre-release filter, pruning young generations. Each made exactly
  one test fail.
- `npm run test:worker` 36 pass, `npm run check:worker` and prettier clean.
- Local workerd (`wrangler dev --test-scheduled` with Hyperdrive pointed at a
  scratch database holding 1.5.5 and 1.6.0, and a throwaway gpg key): the
  cron logged `rebuild: wrote generation 1, 2 releases`, then `unchanged`.
  Every file came back with its content type and cache header; ETag 304,
  HEAD, the pool 302 and the `.repo` origin were right.
- Ubuntu 24.04 container against that workerd: `apt update` verified
  InRelease with the served keyring, and the `.deb` fetched through the pool
  302 had the sha256 listed in `Packages`.
- Fedora 45 container with the served `.repo`: dnf imported the served key
  and checked `repomd.xml.asc` (`repo_gpgcheck=1`); `repoquery` listed 1.5.5
  and 1.6.0 for x86_64 and aarch64. `gpgcheck` was set to 0 for this run,
  since the test RPMs are not signed (LR-08).
- `wrangler deploy --dry-run`: 243.22 KiB, 66.25 KiB gzipped; openpgp.js
  (a test dependency) is not in the bundle.
- Local CPU of a full build, sign and hash, in Node 24 on an Apple M-series
  Mac, averaged over 10 runs after warm-up: 2.1 ms for 1 release, 1.5 ms for
  10, 4.2 ms for 100, 10.2 ms for 300. This is not workerd on Cloudflare,
  and leaves out the database round trips.

### The `develop` preview (2026-11-13)

Deployed by the maintainer from `da84aa7`, the same commit as
`feat/linux-repos`. Checked with curl:

- `/api/health`: 200, `{"ok":true,…}`, so Hyperdrive reaches
  `agent_sessions_demo`.
- `/rpm/agent-sessions.repo`: 200, `max-age=3600`, `baseurl` and `gpgkey`
  on the preview's own address, `gpgcheck=1`, `repo_gpgcheck=1`.
- Every generation file (`InRelease`, `Release`, `Packages`, `repomd.xml`,
  the key files): 404 with `max-age=60`. The preview has `GITHUB_TOKEN` and
  `INGEST_TOKEN` but no `REPO_SIGNING_KEY`, so no rebuild can write a
  generation; this is the intended behaviour without a key.
- No published release has `repo-meta.json` yet (v1.5.6 has its two
  unsigned `.rpm` files and `SHA256SUMS`), so even with a key the
  generation would list no releases.

The maintainer chose not to give the preview a throwaway key. The rebuild's
CPU time and the served signatures are checked on production after the first
release with `repo-meta.json` and signed RPMs (LR-19).
