## Scope

Needs the maintainer:

- Generate the repository key and the RPM key, both Ed25519 as v4 EdDSA
  keys (what `gpg --quick-gen-key … ed25519` makes; not RFC 9580 Ed25519,
  see LR-02), each with a three-year expiry, on an offline machine; keep encrypted
  backups.
- Store the repository key as the Worker secret `REPO_SIGNING_KEY` and the
  RPM key as this repository's secret.
- Write `docs/plan/linux-repos-keys.md`: fingerprints, where each key lives,
  how to extend expiry (with a calendar date six months before it), and how
  to rotate (publish the new public key, sign with both for a release
  cycle, then drop the old).
- Rotation has to follow what LR-13 found: every key in `REPO_SIGNING_KEY`
  signs `Release`, but only the first signs `repomd.xml`. So the new key goes
  in second, and moves first only when dnf users can be expected to have
  it. Check whether dnf fetches the key file again when `repomd.xml.asc`
  switches to a key it has not imported.
- The RPM key's public block goes in `RPM_PUBLIC_KEYS`
  (`web/worker/repo/keys.ts`).

## Acceptance criteria and tests

- Fingerprints in the keys doc match the public key files the Worker

- The rotation steps are tried once with test keys on a preview.

## Done

- `packaging/linux/repo-keys.sh` has the commands `new`, `extend`, `show`,
  `secret`, `backup` and `restore`.
  - It makes v4 EdDSA Ed25519 signing keys, valid for 3 years, with the year
    in the user ID, and refuses any other kind.
  - It exports each key's public, secret and revocation files.
  - `show` prints the renewal date, six months before expiry.
  - `secret` writes one armored block per key, in the order given, for
    `REPO_SIGNING_KEY`.
  - `backup` writes an AES-256 encrypted backup of the whole directory.
- [linux-repos-keys.md](../../plan/linux-repos-keys.md) covers:
  - the keys table, to be filled in;
  - making, backing up and storing the keys, and checking the served
    fingerprints;
  - renewal, the repository key's rotation and the RPM key's rotation;
  - what to do if a key leaks;
  - the checks behind each step.
- Previews never get the production repository key; this is now in the keys
  doc and in the website's README.
- Website commit `b97d968` (fix): the rebuild's inputs hash now covers each
  key's public packets, not only its fingerprint. Before it, extending a
  key's expiry wrote no new generation, so the served keyring kept the old
  expiry.
- New task [LR-21](LR-21.md): ship the keyring in the `.deb`, since apt
  users only get a renewal or rotation by fetching the keyring again. It
  needs the maintainer's decision.

## Evidence

- **The script** ran with throwaway keys in Ubuntu 24.04 (gpg 2.4.4),
  Debian 13 (gpg 2.4.7) and Fedora 45 (gpg 2.4.9). The packets were
  `version 4, algo 22`, with key flags 03 and a 3-year expiry. Results:
  - `secret B A` keeps that order;
  - `extend` moved a 1-year expiry to 3 years;
  - backup and restore round-trip (`show` and the file list match);
  - the error cases each exit 1: a key listed twice, an unknown key, a bad
    role, a missing GnuPG home, a backup over an existing file. A wrong
    backup passphrase exits 2.
  - shellcheck is clean.
- **Rotation and renewal.** The repositories were built by the Worker's own
  `buildFiles` and `loadSigningKeys` and served from fixed URLs. The tables
  in the keys doc give each case's results. In short:
  - **apt** (Ubuntu 24.04 with gpgv, Debian 13 and Ubuntu 26.10 with sqv):
    - a rotation works while both keys sign, including the two-block secret
      from `repo-keys.sh secret`;
    - after the old key is dropped, it works only for users who fetched the
      keyring again;
    - a renewal in time works with the old copy;
    - once the old copy is past its expiry it is refused, even though the
      served key was extended.
  - **dnf** (Fedora 40 dnf4, Fedora 45 dnf5): it fetched the key file again
    and imported the new key when `repomd.xml.asc` switched to it. That
    answers the task's question. It also accepted the extended key with an
    expired copy imported.
  - **loadSigningKeys** on the expired key throws `SigningKeyError`; on the
    extended key it reads the new expiry.
- **The website fix.** A new DB test makes the same key with a new
  self-signature (openpgp.js `reformatKey`). It checks that the rebuild
  writes a new generation whose keyring has the new expiry. The test fails
  without the fix and passes with it. Results: `test:db` 38 pass,
  `test:worker` 36 pass, and `check:worker` and prettier are clean.
- The results are kept in the session's scratch directory; they are not
  committed.

### The real RPM key (2026-11-13)

The maintainer made it and set `RPM_SIGNING_KEY`
in the `release` environment. `gh secret list --env release` shows it, set
2026-11-13 19:49 UTC. Its public half went into the website's
`RPM_PUBLIC_KEYS`.

- `gpg --show-keys` (GnuPG 2.4.9, Fedora 45 container, no network):
  `ed25519 2026-11-13 [SC] [expires: 2029-11-12]`, fingerprint
  `A0B91ED73F0FB8446C41AB6160FDFBC472CBA9C8`, user ID "Agent Sessions RPM
  signing key (2026)". `--list-packets`: version 4, algo 22, key expires
  after 3 years. `--check-sigs`: the self-signature is good.
- The key was made by GnuPG 2.5 (its self-signature has the notation
  `manu=2,2.5+1.12,0,3`), which the procedure had not been tried with. It is
  still a v4 EdDSA key, and `rpm --import` took it on Fedora 40 (rpm
  4.19.1.1, `gpg-pubkey-72cba9c8-6af768f2`) and Fedora 45 (rpm 6.1.0).
- The Worker's `dearmor` reads the entry in `RPM_PUBLIC_KEYS` as one block.
  `npm run test:worker`: 36 passed.
- Not checked: that the secret matches this public key. Only a signed run
  shows that: the release workflow's "Sign the .rpm packages" step, then
  `rpm -K` against this key (LR-19).
