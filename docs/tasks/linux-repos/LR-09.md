# LR-09 — repo-meta.json for .deb files

- **Status:** ✅ Done
- **Estimate:** 3 h
- **Depends on:** —
- **Plan:** [linux-repos.md](../../plan/linux-repos.md)

## Scope

- `packaging/linux/repo-meta.sh VERSION DIST_DIR`: for each `.deb`, the
  `apt-ftparchive packages` stanza for that one file, `Filename:` set to
  `pool/<version>/<file name>`. Writes `dist/repo-meta.json`:
  `{"version": ..., "deb": [{"arch", "file", "size", "sha256", "stanza"}], "rpm": []}`.
- The release workflow runs it in the linux job and uploads it with the
  packages.
- `packaging/release-checksums.sh` requires `repo-meta.json` in the release
  set and checks that every size and hash in it matches the files.

## Likely files

`packaging/linux/repo-meta.sh`, `packaging/release-checksums.sh`,
`.github/workflows/release.yml`, `Makefile`.

## Acceptance criteria and tests

- Golden test on the two 1.5.5 `.deb` files: the stanzas equal
  `apt-ftparchive`'s for those files, apart from `Filename`.
- `release-checksums.sh` refuses a set without `repo-meta.json`, and one
  whose meta disagrees with a package.
- shellcheck passes.

## Evidence

- `packaging/linux/repo-meta.sh VERSION DIST_DIR` copies each `.deb` alone
  into `pool/<version>/` of a scratch folder and runs
  `apt-ftparchive packages pool/<version>` there, so `Filename:` is already
  the repository path. It checks that the paragraph is one, for that file,
  with its size and SHA256, and writes `{"version", "deb": [...], "rpm": []}`
  in file name order (`LC_ALL=C`). It refuses a folder with no `.deb` and a
  version with a slash or spaces.
- **Changed from the scope:** the workflow runs it in the `artifacts` and
  `release` jobs, before `release-checksums.sh`, not in the `linux` job.
  That job is a matrix that builds one architecture per runner, and the file
  covers both. Those jobs install `apt-utils` with the apt-install action.
- `release-checksums.sh` requires `repo-meta.json`. It checks the version,
  that `deb` lists exactly the release's two `.deb` files, every listed
  file's size and SHA256 (`deb` and `rpm`), and that each stanza's
  `Filename`, `Size` and `SHA256` lines match. `SHA256SUMS` covers the file.
- `packaging/linux/test-repo-meta.sh`, run by `make test-repo-meta` in an
  `ubuntu:24.04` container on the published 1.5.5 `.deb` files (checked
  against their `SHA256SUMS`): 20 checks pass.
  - Golden: each stanza equals the paragraph `apt-ftparchive packages`
    writes for the two files in one flat folder, apart from `Filename`,
    which is `pool/1.5.5/<file>`.
  - Version, architectures, order, fields, sizes, hashes; a second run
    writes the same bytes; the two refusals above.
  - `release-checksums.sh` on a full release set (the real `.deb` files and
    stand-ins for the rest) accepts it and lists `repo-meta.json` in
    `SHA256SUMS`. It refuses: no `repo-meta.json`, a wrong size, a wrong
    sha256, a stanza with another hash, a stanza with another `Filename`,
    a missing `.deb`, another version, not JSON, a package changed after
    the meta was written.
  - A mutation check: a `repo-meta.sh` that edits a stanza's `Section` line
    fails the golden checks for both files.
- shellcheck 0.9.0 (Ubuntu 24.04): `repo-meta.sh`, `test-repo-meta.sh` and
  `release-checksums.sh` clean (two older `info` notes in
  `release-checksums.sh` were fixed too).
- actionlint on `release.yml`: only the earlier SC2046 note in the macOS
  job, as before this change.
- Not run: the workflow itself. The new steps first run on the next manual
  Release run or release.
