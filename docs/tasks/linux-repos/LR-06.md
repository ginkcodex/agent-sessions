# LR-06 — Cron catch-up and backfill

- **Status:** ✅ Done. Ran locally against real GitHub; not yet on a preview
- **Estimate:** 2 h
- **Depends on:** LR-05
- **Plan:** [linux-repos.md](../../plan/linux-repos.md)

## Scope

- A `scheduled` handler, hourly: list the ten newest releases, ingest those
  missing or with a different `SHA256SUMS` digest or prerelease flag.
  Then run the rebuild hook whether or not anything changed: an ingest
  whose rebuild failed answered 500 but kept its rows, and ingesting it
  again is a no-op, so only this retries the rebuild (found in LR-05). The
  rebuild stops early when its inputs are unchanged (LR-14).
- `npm run backfill`: pages through every release and ingests each, against
  a given base URL and token, printing what changed.

## Likely files

`web/worker/cron.ts`, `web/scripts/backfill.mjs`, `web/wrangler.jsonc`
(`triggers.crons`).

## Acceptance criteria and tests

- With a fake GitHub listing three releases, one already stored, the cron
  ingests two and leaves the third alone; flipping the stored one to a
  pre-release makes the next run ingest it.
- A GitHub failure during the cron logs and exits without partial rows.
- After a failed rebuild, the next cron run rebuilds although no release
  changed.
- Backfill run twice reports no changes the second time.

## Done

In the website repository (`0c93272`):

- `worker/cron.ts`: `runCron` lists the ten newest releases
  (`GitHub.latestReleases`, new in `github.ts`), leaves out drafts and tags
  that are not `v` plus semver, and compares each with the stored row:
  prerelease flag, and GitHub's digest of `SHA256SUMS` against the SHA-256
  of the stored text. Missing, changed, or without a digest: ingested (the
  LR-05 `ingest`, one transaction each). A release that fails its checks
  or has vanished is logged and skipped; GitHub or the database failing
  stops the run. The rebuild hook runs at the end of every run, whatever
  happened before. It never throws; it logs one summary line.
- `worker/index.ts`: a `scheduled` handler with its own database client;
  the no-op rebuild (until LR-14) is shared with the ingest.
- `wrangler.jsonc`: `triggers.crons` `17 * * * *`.
- `scripts/backfill.mjs`, `npm run backfill -- <site URL>` with
  `INGEST_TOKEN` exported: pages through GitHub's release list (100 a page,
  without a token unless `GITHUB_TOKEN` is set), posts each tag to
  `/api/ingest` oldest first, prints one line per release and a summary.
  It stops at a 401 or 503 (every later call would get the same) and exits
  1 if anything failed.
- Tests share `worker/test/db/helpers.ts` (a database per test, and a fake
  GitHub serving any number of releases, made from the 1.5.5 fixture under
  other versions); the ingest tests moved onto it.
- README: the cron, backfill, and how to run both locally.

## Evidence

- `npm run test:db`: 27 passed (8 migration, 9 ingest, 7 cron, 3 backfill),
  against the compose Postgres 17.
  - Three releases listed, one stored: the other two ingested, the stored
    one not read again; a second run makes one list call and no ingest,
    and still rebuilds.
  - Marking a stored release as a pre-release, then replacing a
    `SHA256SUMS` (another line order, new digest): each ingested once on
    the next run, then no-ops.
  - The list failing (502): nothing written, rebuild ran. The second
    release's `SHA256SUMS` failing: the first written whole, the second
    not at all, the third not tried; the next run catches up on both.
