# LR-16 — Container checks for Ubuntu, Debian and Fedora

- **Status:** 🟡 Partial: ran against `wrangler dev` on arm64; a preview or production run waits for LR-19
- **Estimate:** 3 h
- **Depends on:** LR-14
- **Plan:** [linux-repos.md](../../plan/linux-repos.md)

## Scope

`packaging/linux/verify-repo.sh BASE_URL` runs, in clean containers of
Ubuntu 24.04, Debian 13, newest Ubuntu, Fedora 40 and newest Fedora:

- the documented setup commands, then install;
- `apt policy` / `dnf --showduplicates list` list every expected version;
- install the oldest listed version, then upgrade straight to the newest;
- apt only: keep an old package list, then `apt upgrade` without
  `apt update` and check the download succeeds.
- dnf: the packages signed by `sign-rpms.sh` (LR-08) install with
  `gpgcheck=1`. dnf imports the RPM key from the key file. After an RPM key
  rotation (a release signed by a second throwaway key, its public key added
  to `RPM_PUBLIC_KEYS`), an upgrade imports the new key. This was not
  checked in LR-08 or LR-15.

Usable against `wrangler dev`, a preview, or production.

## Likely files

`packaging/linux/verify-repo.sh`, `Makefile` (`verify-repo`).

## Acceptance criteria and tests

- All five distributions pass against a preview with two releases.
- shellcheck passes.

## Done

- `packaging/linux/verify-repo.sh [--between CMD] [--images "IMAGE..."]
  BASE_URL VERSION...` runs, in parallel, one clean container per image
  (default: `ubuntu:24.04 debian:13 ubuntu:rolling fedora:40
  fedora:latest`):
  1. the documented setup commands; apt runs `apt update`, dnf checks that
     the `.repo` file has `gpgcheck=1` and `repo_gpgcheck=1`, then installs
     the oldest version with signature checks on;
  2. `--between CMD`, once, for example to add a release or a key to a
     Worker on this machine;
  3. apt installs the oldest version from step 1's package lists, without
     `apt update`, so the download goes through an old index;
  4. `apt-cache madison` / `dnf list --showduplicates` must list exactly
     VERSION...;
  5. upgrade straight to the newest; dnf logs the package's signature
     (`%{DSAHEADER:pgpsig}`: EdDSA signatures live there, not in
     `RSAHEADER`) and the keys rpm imported;
  6. the documented removal commands; the package and its binary are gone
     and the package manager no longer offers it.
- The setup and removal lines are the ones README and the website show
  (LR-18); a comment in the script and in the website's
  `test/linux-repos.spec.ts` points at the others.
- The Fedora setup is `curl … | sudo tee /etc/yum.repos.d/…` rather than
  `dnf config-manager`, whose syntax differs between dnf 4 (`--add-repo`)
  and dnf 5 (`addrepo --from-repofile=`). The plan's snippet changed to
  match.
- `make verify-repo REPO_VERSIONS="…" [REPO_URL=…]`; `REPO_URL` defaults to
  the production site.

## Evidence

Both runs used a local `wrangler dev` (port 8799) on a scratch database
(`as_lr16`, LR-14's setup) and served the packages from a local pool
(port 8798) that the `/apt/pool` and `/rpm/` redirects pointed at. The
packages were v1.5.5 and v1.5.6's `.deb` files and their `.rpm` files signed
with `sign-rpms.sh` (LR-08) and throwaway keys. Containers ran in OrbStack
(Docker 29.8.2) on macOS arm64, so only the arm64 packages were tested.

**Run 1: a new release between the steps.** Generation 1 held 1.5.5; the
`--between` script added 1.5.6 (signed by RPM key 1), triggered the cron and
waited for the new `InRelease` and `repomd.xml`. The Worker's cache served
the old ones for 301 s, as their `max-age=300` says.

```
ubuntu:24.04     Ubuntu 24.04.5 LTS (aarch64)             ok
debian:13        Debian GNU/Linux 13 (trixie) (aarch64)   ok
ubuntu:rolling   Ubuntu 26.10 (aarch64)                   ok
fedora:40        Fedora Linux 40 (Container Image) (aarch64) ok
fedora:latest    Fedora Linux 45 (Container Image) (aarch64) ok
```

- apt installed 1.5.5 from the old lists
  (`Get:1 http://host.docker.internal:8799/apt stable/main arm64
  agent-sessions arm64 1.5.5 [44.3 MB]`), through the pool redirect, after
  the index had moved on.
- Every image listed `1.5.5 1.5.6` and ended on 1.5.6.
- This run used an earlier version of the script: it installed on dnf in
  step 5, queried `RSAHEADER` (which printed `(none)` for EdDSA) and had no
  removal step. Run 2 covers all of those.

**Run 2: an RPM key rotation.** The keys procedure's steps 2 and 3: the
`--between` script added a second throwaway RPM key
(`7C05BC5645EC7CBADF06696736D3599895CA35D6`) to `RPM_PUBLIC_KEYS` after the
first, restarted `wrangler dev` with an empty cache (standing in for the
hour the key file stays cached), and added 1.5.6 signed by the second key.
Result: `exit 0`, all five `ok`, with the same lines as run 1.

- Fedora 40 (dnf 4) and Fedora 45 (dnf5): step 1 imported the repository
  key `0x4C7E46E2` and RPM key 1 `0x306C3B25`; 1.5.5 installed with
  `signature: EdDSA/SHA512, …, Key ID fb9a5b5f306c3b25`. The upgrade
  imported the new key ("Importing GPG key 0x95CA35D6" on Fedora 40,
  "Importing OpenPGP key 0x95CA35D6" on Fedora 45) and installed 1.5.6 with
  `Key ID 36d3599895ca35d6`. The rpm database then held the Fedora key, the
  repository key and both RPM keys.
- dnf imports each key twice: once into its own keyring for
  `repo_gpgcheck` at `makecache`, and once into the rpm database at install.
  Both are expected; a user answering yes sees the prompt each time.
- apt, all three: 1.5.5 from the old lists, listed `1.5.5 1.5.6`, upgraded
  to 1.5.6.
- Removal, all five: the package and `/usr/bin/agent-sessions` were gone;
  `apt-cache madison` printed nothing after `apt update`; dnf answered "No
  matching Packages to list".
- `shellcheck packaging/linux/verify-repo.sh`: clean. `make -n verify-repo
  REPO_VERSIONS="1.5.5 1.5.6"` prints the expected command; without
  `REPO_VERSIONS` it stops with a usage message.

**Seen but harmless.** On Ubuntu 26.10, installing systemd-resolved (pulled
in by `curl`) prints `mv: cannot move … /etc/resolv.conf: Device or resource
busy`. Docker mounts that file; it is a container artifact.

**Not checked**

- A preview or production deployment. A preview needs the maintainer's
  Cloudflare account, and both need two releases with signed RPMs, which
  only exist after LR-19 sets `RPM_SIGNING_KEY`. LR-19 runs this script
  against production.
- amd64: only arm64 containers ran. The repositories hold both
  architectures, and LR-11 and LR-12 checked their indexes.
- Packages downloaded from GitHub: the pool was local, so the redirect to
  GitHub's release assets was not followed here (LR-14 checked it).
- dnf-automatic and `dnf upgrade` without `-y`.
