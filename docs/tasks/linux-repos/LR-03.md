# LR-03 — Schema, migrations and local Postgres

- **Status:** ✅ Done. Not yet applied to `agent_sessions_demo` or `agent_sessions_prod`; that is the maintainer's run
- **Estimate:** 2 h
- **Depends on:** LR-01
- **Plan:** [linux-repos.md](../../plan/linux-repos.md)

## Scope

- `web/migrations/0001_releases.sql`: `releases`, `assets`,
  `release_documents`; `0002_repo.sql`: `repo_generations`, `repo_files`,
  `repo_state`; both as in the plan, with a `schema_migrations` table.
- `npm run db:migrate` applies unapplied files in order, each in a
  transaction, using `DATABASE_URL`.
- A Docker Compose Postgres for `wrangler dev` (Hyperdrive's
  `localConnectionString`) and for tests.

## Likely files

`web/migrations/`, `web/scripts/migrate.ts`, `web/compose.yaml`,
`web/wrangler.jsonc`.

## Acceptance criteria and tests

- Migrating an empty database, then again, succeeds the second time with
  nothing applied.
- A failing migration leaves no partial schema and no row in
  `schema_migrations`.

## Done

In `agent-sessions-web`, branch `feat/linux-repos`, commit `71770bd`:

- `migrations/0001_releases.sql`: `releases`, `assets`, `release_documents`.
  - `releases.version` is semver without the `v`; `tag` must be
    `'v' || version`.
  - An asset's `url` must be
    `https://github.com/ginkcodex/agent-sessions/releases/download/v<version>/<name>`,
    so the pool redirects (LR-14) cannot point anywhere else, whatever is
    written to the table. Names have no `/` and do not start with a dot.
  - `deb`, `rpm` and `meta` assets need a `sha256`; `other` ones (such as
    `SHA256SUMS` itself) may lack one.
  - A document must be one of its release's assets, kept as text so it
    stays verbatim. Deleting a release removes its assets and documents.
- `migrations/0002_repo.sql`: `repo_generations` (with an `inputs_sha256`
  so a rebuild can stop early when nothing changed), `repo_files` (`bytea`
  bodies, paths under `apt/` or `rpm/` with no `.` or `..` segments, an
  index on path and generation for hash-named lookups) and a one-row
  `repo_state`. Its `current` generation cannot be deleted.
- `scripts/migrate.mjs`, `npm run db:migrate` with `DATABASE_URL`:
  - applies unapplied files in name order, each in one transaction with its
    `schema_migrations` row (name, sha256, time);
  - a transaction-level advisory lock serializes concurrent runs;
  - refuses, before applying anything, when an applied file was edited or
    is missing from the checkout, and refuses badly named or
    duplicate-numbered files;
  - prints the user, host and database it is about to change (never the
    password; the password can come from `PGPASSWORD`);
  - `--grant <role>` gives the Hyperdrive login read and write on the
    tables, including later migrations' tables, but no DDL, and only read on
    `schema_migrations`. The plan said the Worker never changes the schema;
    this makes the database enforce it.
- `compose.yaml`: Postgres 17 on `127.0.0.1:54329` for `wrangler dev`
  (`localConnectionString` in `wrangler.jsonc`) and the tests.
  `npm run db:up` starts it.
- `npm run test:db`: `node --test` against that Postgres, each test in a
  database of its own.
- The README's Workers section describes the schema, the migrate command
  and local runs.

## Evidence

- `npm run test:db`: 8 passed.
  - Empty database: both files applied; a second run applies nothing.
  - `0003_broken.sql` (create a table, then divide by zero): the run fails,
    the table does not exist, and `schema_migrations` lists only 0001 and
    0002.
  - Two runs at once: each file applied exactly once.
  - An edited applied file, or one missing from the checkout: refused, and
    a new `0003` alongside it was not applied.
  - `3_bad.sql` and a second `0002_*.sql`: refused.
  - Constraints: a non-semver version, a tag that is not `v<version>`, a
    URL outside our release, a name with `../`, a `.deb` without a hash, a
    document that is not an asset: each refused by name. Deleting a release
    removes its rows.
  - `repo_state`: one row, `current` null; a second row is refused; the
    current generation cannot be deleted; bad paths (`apt/../x`, `apt//x`,
    `apt/.hidden`, `other/x`, `apt`) are refused; deleting a generation
    removes its files.
  - `--grant`: as that role, inserts and updates work; `create table`,
    `drop table`, `alter table` and `delete from schema_migrations` are
    refused.
- Mutations:
  - without the advisory lock in the per-file transaction, the concurrent
    test failed in 5 of 5 runs;
  - running the file outside the transaction was not caught by the
    failing-migration test. Postgres already runs a multi-statement simple
    query as one implicit transaction, so the body rolls back by itself;
    the explicit transaction is what ties the body to its
    `schema_migrations` row, and no test makes only that insert fail.
- CLI against the compose database: first run applied both files and
  granted a test role; second run printed `nothing to apply`; no
  `DATABASE_URL`, or an unknown option, exits 1 with a message. A URL
  without a password works with `PGPASSWORD`, and fails without it.
- `wrangler dev` with no environment variable: `/api/health` answered from
  the compose database through `localConnectionString`.
- `npm run check`, `npm run check:worker` and `prettier --check .` pass.
- Not checked: Postgres versions other than 17 (the README notes that 14
  and older let every login create tables in `public` unless revoked), and
  the maintainer's databases, which have not been migrated yet.
