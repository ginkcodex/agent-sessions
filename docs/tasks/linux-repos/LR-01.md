## Done

In `agent-sessions-web`, branch `feat/linux-repos` (commit `7e3c9a7`, not
pushed):

- `worker/index.ts` is the Worker. `assets.run_worker_first` sends
  `/api/*`, `/apt/*` and `/rpm/*` to it.
  - `GET /api/health` runs `select now()` and answers
    `{"ok":true,"now":"…"}`, with `Cache-Control: no-store`.
  - If the database fails, it answers `{"ok":false}` with 503 and logs the
    error. No details go to the client.
  - Other methods get 405.
  - Every other path goes to `env.ASSETS`, so it gets the same file or 404
    page as before.
  - Worker responses carry the security headers from `static/_headers`,
    which applies only to assets.
- `worker/db.ts` connects with postgres.js (`postgres` 4.1.1),
  `max: 5, fetch_types: false`, with a client per request ended in
  `ctx.waitUntil`.
- `wrangler.jsonc`:
  - adds `main`, `nodejs_compat`, the `ASSETS` binding and `observability`;
  - binds `HYPERDRIVE` at the top level to `hyperdrive-agent-db-prod`
    (`agent_sessions_prod`). Its ID is still the placeholder
    `PRODUCTION_HYPERDRIVE_ID`, so a production deploy fails until it is
    filled in;
  - binds `previews.hyperdrive` to `hyperdrive-agent-db`
    (`f0a3d8c613e045d984e2db4556b231d8`, `agent_sessions_demo`).
  - Wrangler's schema confirms that `previews` takes its own `hyperdrive`
    and that bindings are not inherited. Previews therefore never see
    production data.
- Both databases are reached through Cloudflare Tunnels set up by the
  maintainer. Hyperdrive holds the Access token and the login; nothing
  secret is in either repository.
- `npm run check:worker`: `wrangler types` (output git-ignored) and `tsc`
  with `worker/tsconfig.json`.
- `npm run dev:worker`: build, then `wrangler dev`.
- `PLAYWRIGHT_BASE_URL` points the browser suite at a running copy, such as
  `wrangler dev` or a preview URL.
- The README describes the Worker, the bindings and local runs. It also
  notes that Cloudflare Pages can only serve the static part.

### Client choice: postgres.js

Both `pg` 8.23.1 and `postgres` 4.1.1 ran the same test in local workerd
against Postgres 17: `now()`, `version()`, and a transaction that creates a
temp table, inserts parameters (including a quote) and reads them back.
Both passed.

| Client | Bundle | gzip |
|---|---|---|
| `pg` | 195.5 KiB | 40.4 KiB |
| `postgres` | 190.5 KiB | 50.7 KiB |

I chose postgres.js because of how it reads, not how it performs:
- every value in a tagged-template query is a parameter;
- `sql.begin()` commits, or rolls back on a throw, by itself, which the
  ingest's one-transaction write (LR-05) needs.

The 10 KiB of gzip is not a concern; the whole Worker uploads at 51 KiB
gzip.

### CPU budget

Measured in local workerd on the maintainer's Apple-silicon Mac. The clock
advances across `scheduler.wait`, so these are timings of real work.

| Operation | Time |
|---|---|
| gzip 500 KB of Packages-like text with random hashes (CompressionStream) | 2.45 ms (to 83 KB) |
| SHA-256 of 2 MB | 0.70 ms |
| Ed25519 OpenPGP clear-signature of 50 KB (`openpgp` 6.3.2) | 0.55 ms |
| Ed25519 detached signature of 500 KB | 0.45 ms |

A simulated full rebuild:
- parses N renumbered copies of the real v1.5.5 `repo-meta.json`;
- builds `Packages` and `Packages.gz` for both architectures, `Release`,
  `InRelease` and `Release.gpg`;
- builds the three gzipped XML files, `repomd.xml` and `repomd.xml.asc`;
- hashes everything, and reads the armored key.

| Releases | Rebuild | Index files |
|---|---|---|
| 50 (today: 44 tags) | 2.6 ms | 89 KB |
| 300 | 6.4 ms | 522 KB |
| 1000 | 17.2 ms | 1.7 MB |

Decision, pending the preview measurement: the Free plan's 10 ms CPU per
invocation covers today's rebuild with room to spare. It runs out at a few
hundred releases. Database reads and writes add CPU on top: parsing about
7 KB of JSON per release, and writing the files. Cloudflare's CPUs may be
slower than this Mac.
- Cheap way to make room: a rebuild skips the work when the inputs are
  unchanged, and the cron does nothing when nothing changed.
- Remaining choice: if the preview shows a rebuild's CPU time above about
  5 ms, move to Workers Paid.
