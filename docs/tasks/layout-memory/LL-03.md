- **Status:** ✅ Done

## Scope

Remember the window's size and position across runs:

- `internal/app/windowstate.go`: role-keyed store (`primary`, `extra`) of
  normal bounds plus a maximised flag in `window-state.json`, through
  `internal/configfile` atomic writes. Pure helpers for the work-area clamp
  (saved bounds must intersect the nearest screen's work area; otherwise fall
  back to the first-run size) so they are unit-testable without a window.
- Save on `WindowClosing` (hook already registered in
  `cmd/agent-sessions/shell.go`) with `OnShutdown` as backstop. Track the
  normal (un-maximised) bounds from move/resize events so closing while
  maximised saves the pre-maximise size, and the maximised flag.
- Restore in `openWindow`: `SetBounds` the clamped bounds, then `Maximise()`
  when flagged. Fullscreen is not restored.
- First run (no saved state): `min(1500×920, 90% of the work area)`, centered.
- Multi-window: the first window of a run is `primary`, New Window windows are
  `extra` and cascade (+32 px from the opener) when no `extra` state exists.

## Acceptance criteria

- Resize, move, close, reopen restores size and position; maximise, close,
  reopen restores maximised and un-maximising returns the pre-maximise size.
- Saved bounds on a removed monitor reopen fully visible on the remaining
  screen; no negative or off-screen coordinates survive a clamp.
- New Window cascades; each role restores its own saved geometry.
- A malformed or truncated `window-state.json` falls back to the first-run
  size without an error dialog.

- Review hardening (same task, after the first pass): restore uses

  `WindowUnMaximise`/`WindowRestore` events (mapped to the Common IDs on
  Windows and macOS) because a minimised window does not report its
  pre-minimise maximised state at close time.
- **"Doesn't remember maximised" bug hunt (same task, live-verified on
  GNOME/mutter):** the hardening above did not survive real testing. The
  failure was reproduced and root-caused with live experiments — a test build
  driven through EWMH client messages (`GDK_BACKEND=x11`, the session itself
  is Wayland), window state read back with `xwininfo`/`xprop` and
  `window-state.json`. Four root causes, each proven on the device:
  1. *Save clobber.* `remember()` ran twice per close; the closing
     listener's copy raced the window destroy and saved empty bounds —
     `{"x":0,"y":0,"width":0,"height":0}` found verbatim in killed-write
     `config-*.tmp` leftovers. `validState` rejects zero bounds wholesale on
     load, so the whole entry, maximised flag included, was discarded.
     Fixed: save only in the closing hook (pre-destroy), never adopt
     zero-sized bounds, and `configfile.WriteAtomic` now sweeps stale
     `config-*.tmp` files (`staleTempAge`).
  2. *Blind creation dropped the flag.* `initialState`'s `screen == nil`
     branch returned only width and height — always taken for the first
     window, which `run_gui.go` creates before `desktop.Run()` when Wails'
     screen APIs return nothing. Fixed: keep the saved state whole there and
     re-check placement from the `WindowShow` listener once screens exist.
  3. *GTK drops pre-show maximises.* `StartState` on Linux maps the window at
     its minimum size without the saved geometry and Wails' post-show
     placement move drops the pending maximise again — and the min-size map
     poisons the un-maximise restore rect (proven: un-maximise collapsed to
     960×600). Fixed: `StartState` is set on Windows and macOS only; on
     Linux a `Common.WindowShow` listener asks `Maximise()` after the show.
  4. *Y drift of +74 px per open/close cycle.* On GTK/X11 the window manager
     reads `XMoveWindow` as the **frame** position while `Bounds()` reports
     the **client** origin, a `_NET_FRAME_EXTENTS` top margin apart (measured
     on the device: `move(300,400)` → reported `(300,474)`, extents
     `[0,0,74,0]`). Save and restore therefore disagreed by a constant and
     the window walked down the screen every run. Fixed with `place()`: ask,
     let the move land (asynchronous, measured under 100 ms), read the
     landing back, ask again for the difference — the constant offset
     cancels and the reported bounds land exactly on the saved corner. The
     maximised ask waits for the placement to settle, so the window
     manager's un-maximise restore rect is the corrected one.
  Live proof with the final binary: seeded `maximised:true` opens
  `_NET_WM_STATE_MAXIMIZED_HORZ/VERT`; closing it re-saves the seed
  (`{"x":200,"y":224,"width":1200,"height":800,"maximised":true}`)
  byte-identical over repeated open/close cycles — the drift is gone;
  un-maximise lands the client exactly at the saved corner (no min-size
  collapse); a windowed close saves real bounds without the flag; no
  `config-*.tmp` leftovers. Wayland note: GDK there can neither report nor
  set window positions — `Bounds()` X/Y read `0,0` and moves are no-ops, so
  size and the maximised flag (the user-visible part) persist while position
  memory is best effort and left to the compositor; `place()` recognises the
  constant `0,0` and stays out of the way.
- **Maximised restore, second pass (same task, live-verified on GNOME 50 /
  GTK 4.22, Wayland and `GDK_BACKEND=x11`):** three more faults, found with
  temporary event logging (`IsMaximised`, `Bounds()` per event, scripted
  un-maximise/reload/close) in an isolated `XDG_CONFIG_HOME`:
  1. *Wayland opened normal, then jumped to maximised.* The post-show
     maximise waited for the page load plus the 300 ms `place()` settle
     (maximise at ~590 ms after start). On Wayland a pre-show `StartState`
     maximise is clean: tested, the window maps maximised (maximise at
     ~170 ms, before the show) and un-maximises to the saved 1500×920.
     Fixed: `app.MaximiseBeforeShow` picks `StartState` for GTK on Wayland
     only (`GDK_BACKEND` first entry, else `WAYLAND_DISPLAY`); X11 keeps the
     post-show path, where `StartState` was re-measured to still collapse
     un-maximise to 960×600.
  2. *Reload re-maximised.* On Linux `Common.WindowShow` is the webview's
     load-finished event, so every reload re-ran the show listener and
     maximised a window the user had un-maximised (reproduced). On Windows
     it fires on every hide/show. Fixed: the listener runs once
     (`sync.Once`).
  3. *Windows and macOS maximised off-screen (code reading, not run).* Wails
     applies `StartState` before it moves the new window to `X`/`Y`
     (`webview_window_windows.go` `run`, `webview_window_darwin.go`), so the
     maximised window was shifted to the saved corner at maximised size.
     Fixed: those platforms no longer set `StartState`; the first show
     clamps if needed and then maximises, without the X11 settle delay.
  Live results with the fixed build: Wayland seed `maximised:true` opens
  maximised from the first frame, re-saves identically over two cycles,
  un-maximises to 1500×920, and a reload after un-maximise stays normal;
  X11 seed `{200,224,1200×800,maximised}` opens maximised, un-maximises to
  exactly that rect, reload stays normal, cycles re-save the seed.
  `go test ./...` green, `TestMaximiseBeforeShow` added; `go vet` clean for
  linux and `GOOS=windows`. Not checked: a real Windows or macOS run (LL-04).
