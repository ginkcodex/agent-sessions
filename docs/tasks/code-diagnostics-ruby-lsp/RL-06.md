## Outcome

- `codeLanguages.ts`: Ruby's providers are `rubocop` and `ruby-lsp`.
  `codeCheckLabels.ts`: the row reads "Ruby language server (ruby-lsp)".
- `CodeChecks.svelte`: the Ruby setup paragraph describes ruby-lsp (never
  downloaded, same Ruby as RuboCop, the version Gemfile.lock locks else the
  newest installed gem, not through `bundle exec`, no add-ons, evaluates the
  Gemfile, reports no problems, may answer nothing while it indexes). The
  install hints add `gem install ruby-lsp`. The approval text lists "ruby-lsp
  for Ruby" among the navigation servers and says RuboCop *alone* gives no
  Ruby navigation. A Ruby project where only ruby-lsp is registered still
  gets the Ruby text.
- `codeNavigation.ts`:
  - `navigationBlocker` leaves lint-only providers (RuboCop) out when it
    looks for an available, missing, unusable or failed server. The "No
    language server provides go to definition…" message shows only when
    every server for the file is lint-only. Beside ruby-lsp, RuboCop's state
    never decides the reason.
  - New `emptyNavigationAnswer`: an empty Ruby answer adds "ruby-lsp may
    still be indexing the project; try again in a moment." `FileViewer`
    shows that longer notice for 4 s instead of 2 s.
- Differences from the brief:
  - The version-floor and incompatible-gem messages are the backend's
    `notice` and failure text (RL-03/RL-04). The UI shows them as they are
    and adds no wording of its own.
  - A missing ruby-lsp reads "ruby-lsp is not installed on this host; Code
    checks shows how to get it." (the general missing-server message), not
    the lint-only message.
  - Fixed along the way: a failure message that ends in a period (ruby-lsp's
    exit-3 text) gave "add-ons.." in the not-running reason; the trailing
    period is now dropped. A RuboCop test regex that could never match
    ("navigation with available") is replaced by one that reads the real
    approval list.
