# SN-06 — One swipe, one step

- **Status:** ✅ Done
- **Estimate:** 2 h
- **Depends on:** SN-05
- **Plan:** [swipe-navigation-windows-linux.md](../../plan/swipe-navigation-windows-linux.md)

## Scope

Found after SN-05 on Windows and Linux: swipes in a row navigate, but a
single swipe could go more than one step through the history.

- **Windows:** SN-05 started a new stroke whenever the speed fell to half
  its peak and rose again for two events. Fingers on a touchpad wobble that
  much all the time, so one swipe split into several strokes, and each
  swiped once. A simulation of jittery swipes (per-event speed ±35 % around
  the peak) stepped twice in 44 of 1000 swipes; with ±50 % over a longer
  swipe, in 995 of 1000.
- **Linux:** a gesture also ended after a 200 ms pause, which is only needed
  where GTK sends no `scroll-end` (X11). On Wayland, fingers resting on the
  pad mid-swipe and then moving on went a second step.

The fix:

- **Windows:** a new stroke needs the fingers to let go first. The speed
  must fall to a quarter of the peak (`STROKE_DECAY` 0.25), through at least
  three falling events in a row (`STROKE_FALL_EVENTS`). Then it must rise
  for two events, as before. Letting go looks like that: the fingers slow
  down, then momentum decays, or it stops when the fingers touch down again.
  A wobble does not. If one swipe runs straight into the next with no
  let-go, that is one step short, never one too many.
- **Linux:** once GTK has sent a `scroll-end`, only `scroll-begin` and
  `scroll-end` bound a gesture. The 200 ms gap stays for X11.

## Acceptance criteria and tests

- Unit test: a swipe whose speed keeps dipping under half its peak and
  rising again steps once; a touch-down in the momentum, then a new swipe,
  steps again; a swipe that runs into the next with no let-go steps once.
  It fails on the SN-05 rule. The SN-05 tests pass unchanged.
- `npm test`, `npm run check`, `go vet` and `go test` (desktop tags) pass.

## Evidence

- `swipeNavigation.ts`: `risesAgain` counts falling events in a row (equal
  counts as falling) and sets `released` at three falls with the speed at
  most a quarter of the peak. A new peak clears it. Only a rise after
  `released` starts a stroke.
- `mousenav_linux.c`: `Swipe.ends` is set on the first `scroll-end`; after
  that the 200 ms gap no longer starts a gesture.
- A throwaway simulation (not checked in), 1000 seeded swipes per case.
  Each case counts the runs that did not give exactly the expected steps:

  | Case | SN-05 rule | This rule |
  |---|---|---|
  | One swipe, ±35 % jitter | 44 | 0 |
  | One long swipe, ±50 % | 995 | 0 |
  | One very long swipe, ±60 % | 1000 | 0 |
  | Slow swipe (peak 6 px), ±50 % | 223 | 0 |
  | Two swipes, the second starting in the momentum at 50 %, 30 %, 20 % or 10 % of the peak, or after it (each case gave the same count) | 89 | 0 |

  A rule with half-speed decay and three falls still split long swipes (511
  of 1000); a third with three falls still split very long ones (659).
- Test (`search.test.mjs`): `one swipe is one step, however its speed
  wobbles while the fingers are down`. It fails with the SN-05 rule (an
  extra step) and passes now.
- `npm test`: 1143 pass, 0 fail (1 skipped, as before). `npm run check`:
  0 errors, 0 warnings. `go vet` and `go build -tags desktop,production
  ./cmd/agent-sessions/` succeed on Linux with GTK 4. `go test` passes for
  that package.
- Not checked: real touchpad streams on Windows (SN-03), and whether GTK
  sends `scroll-end` on Wayland and X11 as assumed (SN-04). In the
  simulation the second swipe starts with a small delta. If a real
  touch-down in fast momentum starts fast instead, that swipe joins the
  last one and is lost.
