# PF-10 — Codex checkpoint reuse

- **Status:** ✅ Done
- **Estimate:** 3 + 3 h
- **Depends on:** PF-01
- **Plan:** [performance.md](../../plan/performance.md)

**Status notes:** reopened 2026-10-25; split into PF-10A and PF-10B before coding. PF-10A and PF-10B complete 2026-10-25. It was blocked on PF-07 because both change the Codex scan and source files. PF-07's outcome is now final (production opt-out), so the dependency is dropped. Milestone 2 raised the value: the IT-06 resolver scans on every Codex load and append, so this cost is now on the live path.

**Goal:** avoid unchanged-source decode/re-encode work without changing canonicalization.

**Current cost** (`internal/provider/codex/scan_rollout.go`, 2026-10-25). For each
unchanged rollout, every scan does:

1. a decode in `scanSource` before the size/mtime skip;
2. a decode and a re-encode in the canonical-overlay pass, which writes
   `Canonical` into every source state;
3. a decode of the previous state, to build the old canonical set for
   Changed/Removed.

That is 3 decodes and 1 encode per source: 192 and 64 for 64 sources (PF-01,
PF-15). The IT-12 warm append with 64 extra rollouts costs 16.6 ms, 19 MB and
285k allocations, against 0.7 ms with none.

**Likely files:** `internal/provider/codex/scan_rollout.go`, `resolve.go`, scan,
index and resolver tests, `BenchmarkCodexResolution` and PF-01 scan benchmarks.

Shared rules for both parts (the original acceptance, unchanged):

- Reuse validated checkpoint state or summaries with bounded memory and explicit
  invalidation. Preserve raw rollout metadata separately from canonical overlays.
- Keep index disappearance, authoritative parent changes, archive changes,
  duplicate selection and fallback correct even when rollout bytes do not change.
- Do not drop deduplication maps just to save memory, and do not rewrite the
  persisted checkpoint schema or version unnecessarily.
- Previously returned `ScanState` objects and checkpoint bytes stay immutable.
- The returned `ScanResult` (Changed, Removed, metadata and diagnostics) is
  identical to the current code's. Reused checkpoint bytes decode to the same
  checkpoint the current code would encode.

**Done when** (across both parts): operation counts fall on unchanged scans;
parity tests cover index addition/removal/change, duplicates, source
deletion/replacement, versions and appends; retained-state cost is recorded;
and the IT-12 `BenchmarkCodexResolution/64extra/warm-append` and the PF-01 Codex
unchanged-scan benchmarks are repeated with before/after numbers in `docs/perf.md`.

## PF-10A — Decode once per scan, skip unchanged re-encodes (3 h; PF-01)

**Status:** complete 2026-10-25; [evidence](../../perf.md#pf-10a--decode-once-per-scan-2026-10-25). An unchanged
scan does 64/0 decodes/encodes for 64 sources (from 192/64); a warm Codex append
with 64 extra rollouts takes 3.4 ms instead of 16.7 ms.

- Carry the decoded checkpoint from `scanSource` in `sourceScan`, so the overlay
  pass and the previous-state pass reuse it instead of decoding again. The
  previous-state pass decodes only sources whose prev bytes differ from what
  `scanSource` already decoded (removed, changed or unreadable sources).
- In the overlay pass, keep the existing checkpoint bytes when the new canonical
  overlay equals the one already stored; encode only when it changes.
- Count work with the existing `CheckpointDecodes`/`CheckpointEncodes`.

**Done when:** an unchanged scan does 1 decode and 0 encodes per unchanged
source (from 3 and 1). Parity tests compare `ScanResult` and decoded checkpoints
against the current behaviour for the cases above, and include an overlay
change on an unchanged rollout (index edit, parent edge, archive flag, duplicate
winner change) that must still re-encode.

## PF-10B — Cross-scan decoded checkpoint cache (3 h; PF-10A)

**Status:** complete 2026-10-25; [evidence and limits](../../perf.md#pf-10b--cross-scan-checkpoint-cache-2026-10-25).
Warm unchanged 64-source scans do 0 decodes/encodes; warm append with 64 extras
falls from 3.47 to 2.36 ms and 81k to 11k allocations. Bounded immutable entries,
raw/version validation, failure/cancellation and concurrent-scan regressions pass.

- A provider-private, size-bounded cache of decoded checkpoints, keyed by path
  and validated by the exact checkpoint bytes and version, so a hit is never
  trusted on size/mtime alone. Entries are immutable; callers get copies or
  read-only values.
- Shared by catalog scans and the IT-06 resolver. Over the cap, entries are
  evicted and the scan decodes as in PF-10A. A cancelled or failed scan does not
  publish entries.

**Done when:** a warm unchanged scan does 0 decodes for cached sources; the
cache is covered by cold, new-provider, reset, version-change, append, rewrite,
cap/eviction and concurrent-scan (race) tests; retained bytes per source are
recorded; and the benchmarks above show the warm-append cost with 64 extra
rollouts approaching the 0-extra case, or the remaining cost is explained.
